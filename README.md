## 왜 만들었나

Claude Code 는 유능하지만 매번 같은 방식으로 일하지는 않습니다.
확인하지 않은 것을 단정하고, 시키지 않은 범위를 고치고, repo 마다 다른 커밋 스타일을 무시하고,
"에러가 없다" 를 "동작한다" 로 보고합니다.

이 repo 는 그 편차를 없앱니다.
좋은 습관을 매번 부탁하는 대신, **지킬 수밖에 없는 구조로 바꿔 두는 것**이 목표입니다.

문서에만 적힌 규칙은 세션이 바뀌면 지켜지기도 하고 안 지켜지기도 합니다.
그래서 훅이나 스크립트로 막을 수 있는 것은 문서에 맡기지 않습니다.

| 층위 | 무엇을 | 어떻게 |
|------|--------|--------|
| **규칙** | 추정 금지, 범위 준수, 응답 형식 | 모든 세션에 항상 로드됩니다 |
| **절차** | 실증 검증, 배포 반영 확인 | 승인 없이는 다음 단계로 못 넘어갑니다 |
| **차단** | 시크릿 유출, 커밋 메시지 규칙 | git 훅이 커밋 자체를 막습니다 |
| **근거** | repo 별 커밋·코드 스타일 | 스크립트가 로그에서 뽑아 표로 냅니다 |

## 설치

```sh
git clone https://github.com/jollaman999/jolla-s-super-skills.git ~/ai/skills
cd ~/ai/skills
./install.sh
```

클론 위치는 자유입니다. 실행하면 **어디에 설치할지 물어봅니다.**

| 범위 | 위치 | 적용 대상 |
|------|------|-----------|
| 전역 | `~/.claude` | 모든 프로젝트 |
| 프로젝트 | `<프로젝트>/.claude` | 그 프로젝트만 |

전역이 기본입니다. 전역 설정을 건드리기 싫거나, 팀 repo 에 규칙을 같이 두고 싶을 때
프로젝트를 고르세요. 파이프나 CI 처럼 물어볼 수 없는 자리에서는 전역으로 갑니다.

```sh
./install.sh --global                # 묻지 않고 전역
./install.sh --project ~/work/api    # 그 프로젝트에만
./install.sh --copy                  # 링크 대신 복사 (링크를 못 만드는 환경)
./install.sh --dry-run               # 무엇을 할지만 봅니다
./install.sh --force                 # 기존 파일을 .bak 으로 옮기고 덮어씁니다
./install.sh --uninstall             # 이 스크립트가 설치한 것만 지웁니다
```

심볼릭 링크로 걸기 때문에 repo 를 `git pull` 하면 바로 반영됩니다.
링크가 아닌 파일이 이미 있으면 건드리지 않고 멈춥니다.

**프로젝트 설치를 쓰면** 문서에 적힌 `~/.claude/skills/...` 경로를
`<프로젝트>/.claude/skills/...` 로 바꿔 읽으세요. 배치는 같습니다.

## Windows

네이티브 Windows 에서는 **Git for Windows 가 필요합니다.**
Claude Code 는 Git for Windows 가 있으면 Bash 도구를 Git Bash 로 실행하고,
없으면 PowerShell 만 씁니다. 이 repo 는 전부 bash 스크립트라 Git Bash 가 있어야 동작합니다.

WSL 을 쓰신다면 리눅스와 같습니다. 아래는 네이티브 Windows 기준입니다.

| 항목 | 필요 | 없으면 |
|------|------|--------|
| Git for Windows | 필수 | Bash 도구 자체가 없어 아무것도 실행되지 않습니다 |
| 심볼릭 링크 | 개발자 모드 또는 관리자 권한 | `install.sh` 가 복사 설치를 제안합니다 |
| `sshpass` | 비밀번호 SSH 를 쓸 때만 | 해당 항목이 `unknown` 으로 나옵니다. **SSH 키를 쓰세요** |
| Docker Desktop | 컨테이너 헬스 체크를 쓸 때만 | 그 항목만 건너뜁니다 |

설치 전에 무엇이 없는지 먼저 봅니다. 아무것도 바꾸지 않습니다.

```sh
./doctor.sh
```

개발자 모드가 꺼져 있으면 `ln -s` 가 링크를 못 만들고 **말없이 복사**합니다.
복사로 설치되면 이 repo 를 `git pull` 로 갱신해도 설치된 쪽은 옛날 그대로인데,
겉으로는 링크와 구분이 안 됩니다.

그래서 `install.sh` 는 링크를 건 뒤 **그게 정말 링크인지 다시 확인합니다.**
복사로 떨어졌으면 그 항목을 `실패` 로 적고 설치를 중단합니다.

복사로 쓰시려면 `--copy` 를 붙여 다시 실행하세요. 복사인 걸 알고 설치합니다.
대신 이 repo 를 갱신할 때마다 `install.sh` 를 다시 실행해야 반영됩니다.

## 세 가지 원칙

**추정을 사실로 말하지 않습니다.**
코드가 그렇게 쓰여 있다는 것과 실제로 그렇게 동작한다는 것은 다른 주장입니다.
실행한 명령의 출력, 직접 접속해서 본 것, `file:line` 중 하나가 없으면 단정하지 않습니다.

**"에러가 없다" 는 통과가 아닙니다.**
가장 흔한 실패는 예외가 아니라 조용히 틀린 값을 내는 무음 실패입니다.
기대한 동작의 흔적이 관측돼야 통과입니다. 통과 판정에는 반증을 한 번 더 붙입니다.

**범위를 넘지 않습니다.**
지시받은 대상 밖은 고칠 게 보여도 보고만 합니다. 고칠지는 사람이 정합니다.

## 고칠 때

문서에 경로를 쓸 때 두 가지가 섞입니다. **읽으라고 가리키는 경로**와 **그대로 복사해 실행할 명령**입니다.
이 둘은 기준이 다릅니다.

| 무엇 | 어떻게 | 예 |
|------|--------|-----|
| 다른 문서를 가리킬 때 | skill 폴더 기준 상대경로 | `verify-impl/SKILL.md` 안에서 `references/ssh.md` |
| 실행할 명령을 적을 때 | `~/.claude/skills/...` 절대경로 | `~/.claude/skills/verify-impl/scripts/ssh-run.sh` |

명령을 상대경로로 적으면 안 되는 이유가 있습니다. 그 명령이 실행되는 곳은 **사용자의 프로젝트
디렉터리**이지 skill 폴더가 아닙니다. `~/git/myapp` 에서 작업하다가 `scripts/ssh-run.sh` 를 실행하면
`~/git/myapp/scripts/ssh-run.sh` 를 찾다가 실패합니다.

```sh
scripts/ssh-run.sh VF-01 '...'                             # 안 됩니다
~/.claude/skills/verify-impl/scripts/ssh-run.sh VF-01 '...' # 이렇게
```

클론 위치(`~/ai/skills` 같은 것)는 어느 문서에도 넣지 않습니다. 사람마다 다르기 때문입니다.
설치하면 `~/.claude/skills/` 아래로 링크가 걸리므로 그 경로를 씁니다.
