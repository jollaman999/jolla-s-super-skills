# 대기 중 보고 - 물어야만 알게 하지 않는다

빌드 30분, 배포 대기, 관측 90분처럼 **내가 답을 못 내는 동안 시간이 흐르는 것**을 대기라고 한다.
대기 중에 아무 소식이 없으면 사용자는 물어야만 상태를 알게 된다.

> "지금은?"
> "끝났냐"
> "얼마나 걸려?"
> "보고있는거야?"
> "진행상황 중간중간 보고해"

세션 기록에서 이런 말이 19번 나왔다. 전부 **내가 먼저 냈으면 나오지 않았을 말**이다.

## 진행 상황 중계 금지와의 경계

`reporting.md` 의 "진행 상황 중계" 금지와 `CLAUDE.md` 의 "진행 상황은 결과가 나온 뒤에 쓴다" 는
그대로 유효하다. 이 문서는 그 규칙의 예외가 아니라 **다른 것을 가리킨다.**

| | 계속 금지 | 이 문서가 다루는 것 |
|---|---|---|
| 무엇 | 한 턴 안에서 다음에 뭘 하겠다는 예고 | 결과 없이 사람이 기다리는 시간 |
| 언제 | 도구를 부르기 직전 | 빌드·배포·관측이 도는 동안 |
| 예 | `"이제 로그를 확인하겠습니다"` 를 쓰고 도구를 부른다 | 빌드를 걸어 놓고 30분이 지난다 |
| 왜 | 도구를 부르면 곧바로 결과가 나온다. 예고는 읽을 값이 없다 | 결과가 없는 동안에도 사람은 기다린다. 침묵은 정보가 아니다 |

한 줄로: **바로 결과가 나오면 결과만 낸다. 결과가 한참 뒤에 나오면 기다리는 동안을 알린다.**

## 판정 - 언제부터 대기인가

| 예상 소요 | 어떻게 |
|-----------|--------|
| 5분 이하 | 대기가 아니다. 그냥 끝내고 결과만 낸다 |
| 5분 초과 | 대기다. 시작 한 줄을 내고 주기를 잡는다 |
| 얼마나 걸릴지 모름 | 대기로 본다. 모르는 채로 붙잡고 있는 쪽이 제일 길어진다 |

5분은 사용자가 "이거 돌고는 있나" 를 의심하기 시작하는 지점이다. 묻기 전에 낸다.

## 대기를 시작할 때 한 줄

**아래가 다 들어가야 한다.** 하나라도 빠지면 그것을 사용자가 물어야만 알게 된다.

| 넣을 것 | 빠지면 나오는 말 |
|---------|------------------|
| 무엇이 도는지 | "보고있는거야?" |
| 언제 다시 볼지 | "지금은?" |
| 무엇이 나오면 끝인지 | "끝났냐" |

```markdown
이미지 빌드를 걸었습니다. 2분 뒤에 한 번 보고 그 뒤로는 5분 간격으로 봅니다.
`Successfully tagged` 가 나오면 끝입니다.
```

시작 한 줄과 중간 보고도 사용자가 쓴 언어로 쓴다. 짧은 줄일수록 영어로 새기 쉽다
(증상: 한국어로 대화하던 세션에서 `"Apply is running against the test VMs..."` 같은 영어 진행 줄이 수십 번 나갔다).

걸리는 시간을 모르면 모른다고 적는다. 지어내지 않는다 (아래 "안 쓰는 것").
같은 작업을 전에 돌린 기록(지난 빌드 로그, 지난 보고)이 있으면 그 시간을 근거와 함께 적는다.
근거가 있는 예상은 지어낸 것이 아니다. 빠지면 "얼마나 걸리냐" 를 듣는다.
**먼저 프로젝트 메모리에서 같은 작업의 단계별 시간을 찾는다** (아래 "끝났을 때" 에서 남긴 것).

## 어떻게 기다리나 - 백그라운드 + Monitor

**5분 넘는 대기는 한 턴 안에서 붙잡고 있을 수 없다.** 앞에서 도는 명령은 최대 10분이고 `sleep` 은 막혀 있다.
그래서 백그라운드로 돌리게 되는데, 백그라운드 작업은 **끝났을 때 한 번만** 알린다.
"끝나면 알림이 옵니다" 만 내고 턴을 끝내면 그 사이 보고가 하나도 없다.

| 할 것 | 왜 |
|-------|-----|
| 작업은 백그라운드로 돌리고, 진행을 보는 Monitor 를 따로 붙인다 | Monitor 의 출력 줄마다 내가 깨어나서 보고할 수 있다 |
| Monitor 가 아래 "주기" 표의 간격으로 한 줄씩 내게 한다 (경과 시간, 지금 단계, 로그 마지막 줄) | 변화가 없을 때도 줄이 나와야 "아직 없다" 를 낼 수 있다 |
| 끝 조건과 횟수 상한을 같이 건다 | 끝 조건이 없으면 안 끝나고, 상한이 없으면 멈춘 작업을 영원히 본다 |
| Monitor 가 만료되면 다시 건다 | 기한이 지나면 조용히 끝난다 (`Monitor expired after 30m` 를 실제로 봤다) |

완료만 기다리는 루프(`until grep -q DONE log; do sleep 20; done`)를 백그라운드로 돌리는 것은 Monitor 가 아니다.
그것은 끝날 때 한 번 알릴 뿐이라 중간 보고가 없다.

## 주기 - 처음은 이르게, 뒤로 갈수록 늘린다

| 예상 대기 | 첫 확인 | 그다음 |
|-----------|---------|--------|
| 5~15분 | 2분 뒤 | 5분 간격 |
| 15~60분 | 3분 뒤 | 10분 간격 |
| 1시간 넘음 | 5분 뒤 | 15~30분 간격 |

**첫 확인을 이르게 두는 이유**는 시작 자체가 실패하는 경우가 가장 흔하기 때문이다.
명령 오타, 권한, 없는 이미지 같은 것은 30분 뒤에 알 일이 아니다.

**아무 일이 없어도 낸다.** "아직 없다" 도 사용자가 기다려도 되는지를 정하는 정보다.

> "1분지난거같은데 안나도보고해"

| 확인해 보니 | 낼 것 |
|-------------|-------|
| 도는 중 | `"12분 경과. 아직 컴파일 단계. 다음 확인 10분 뒤"` |
| 아무 변화 없음 | `"5분 경과. 로그에 새 줄 없음. 그대로 기다립니다"` |
| 예상보다 길어짐 | 길어졌다는 사실을 그대로 낸다. 상한을 다시 잡을지 묻는다 |

## 상한 없는 관측은 `/loop` 로 넘긴다

재발 감시나 야간 모니터링처럼 **끝이 정해지지 않은 것**을 한 턴 안에서 붙잡고 있지 않는다.
턴이 끝나면 관측도 같이 죽고, 그동안 사용자는 다른 것을 시키지 못한다.

| 이런 것 | 어디로 |
|---------|--------|
| 끝이 정해진 대기 (빌드, 헬스, 배포 반영) | 이 문서의 주기대로. 5분이 넘으면 위 "백그라운드 + Monitor" |
| 끝이 안 정해진 관측 (재발 감시, 상태 지켜보기) | `/loop` |

넘길 때 프롬프트에 적을 것.

| 적을 것 | 왜 |
|---------|-----|
| 무엇을 볼지, 무엇을 보고할지 | 안 적으면 매 회차가 다른 것을 본다 |
| 무엇이 나오면 루프를 끝낼지 | 종료 조건이 없으면 끝나지 않는다 |

## 재촉을 받으면 내가 늦은 것이다

사용자가 상태를 먼저 물었으면 **주기 판단이 틀렸다는 신호**다.

| 할 것 | 안 할 것 |
|-------|----------|
| 지금 상태를 바로 낸다 | 사과 문장 |
| 다음 대기부터 간격을 줄인다 | 왜 안 냈는지에 대한 설명 |

사과에는 읽는 사람이 쓸 정보가 없다. 간격만 고친다.

## 사람 없이 돌릴 때 - 넘기기 전에 끝까지 갈 수 있는지 본다

밤새 빌드처럼 **사람이 자리를 비운 동안 도는 작업**은 실패해도 아무도 모른다.
사용자가 돌아와 물을 때까지 몇 시간이 그냥 지나간다.

실제로 겪은 것 (2026-10-28): 밤새 커널 빌드·설치·재부팅을 systemd 유닛에 넘겼다. 02:25 에
zfs 모듈 빌드가 `No space left on device` 로 멈췄고, 아침에 사용자가 물어서야 알았다. ccache 가 12G 를
차지하고 있었다. 다시 띄운 실행은 첫 실패가 남긴 빌드 디렉터리 때문에 또 실패했다.

**넘기기 전에 볼 것.**

| 볼 것 | 어떻게 |
|-------|--------|
| 파이프라인 **전체**가 쓸 디스크 | 첫 단계가 아니라 끝 단계까지 합친다. 지난 실행의 산출물·캐시 크기를 근거로 적고, 남은 공간과 비교한다. 모자라면 넘기지 않고 알린다 |
| 캐시·임시 디렉터리가 어느 파티션에 쓰는지 | `df` 로 보는 곳과 실제로 쓰는 곳이 다를 수 있다 (ccache, `TMPDIR`, 빌드 디렉터리) |
| 메모리 | 병렬 빌드 수(`-j`)가 메모리를 넘기지 않는지 |
| 지난 실패가 남긴 것 | 다시 돌리기 전에 반쯤 만들어진 빌드 디렉터리·잠금 파일을 지운다. 지울 경로는 풀어 적고 무엇을 지웠는지 보고에 남긴다 |
| 실패를 어떻게 알게 되나 | 단계마다 시각과 결과를 로그 파일 한 곳에 적게 한다. 돌아온 사람이 그 파일 하나로 어디서 멈췄는지 안다 |

**넘기는 한 줄에 위 확인 결과를 넣는다.** 디스크를 봤다면 몇 G 가 필요하고 몇 G 가 남았는지,
안 봤다면 안 봤다고 적는다.

```markdown
빌드·설치·재부팅을 `build-nightly` 유닛에 넘겼습니다. 지난 실행 기준 디스크 18G 가 필요하고 /home 에 41G 남았습니다.
단계별 결과는 `/var/log/build-nightly.log` 에 시각과 함께 남습니다.
```

### 돌아온 사람에게 첫 보고

**사용자가 마지막으로 말한 시각부터 지금까지를 다룬다.** 그 앞은 이미 아는 것이라 다시 쓰지 않는다.
경과를 시간 순으로 늘어놓으면 정할 것이 맨 아래에 묻힌다. 응답 형식의 세 줄에 이렇게 채운다.

| 줄 | 채울 것 |
|----|---------|
| 확정된 사실 | 어디까지 끝났고 어디서 멈췄는지. 멈췄으면 그 시각과 로그 경로 |
| 할 일 | **사용자가 정해야 하는 것.** 없으면 "정하실 것 없음" 이라고 쓴다 |
| 확인 못 한 것 | 자리를 비운 동안 아무도 안 본 것 |

자리를 비운 사이에 처음 생긴 이름(유닛·브랜치·파일)은 그 자리에서 풀어 쓴다. 돌아온 사람은 그 이름을 처음 본다.

## 끝났을 때

**기다린 시간과 판정을 같이 낸다.** 시간을 빼면 "그래서 얼마나 걸린 거야" 를 다시 묻게 된다.

```markdown
빌드 끝났습니다. 27분 걸렸고 `Successfully tagged` 확인했습니다.
```

**30분이 넘은 작업은 단계별 시간을 프로젝트 메모리에 남긴다.** 다음에 같은 작업을 돌릴 때
시작 한 줄의 예상 시간 근거가 된다. 한 프로젝트에서 커널 빌드를 몇 번이나 돌렸는데 남긴 시간이 없어서
한 세션에서 "얼마나 걸려" 를 여섯 번 들었다.

| 남길 것 | 예 |
|---------|-----|
| 날짜, 대상, 조건 | 2026-11-01, 커널 7.3 generic, `-j16`, ccache 비어 있음 |
| 단계별 시간 | 컴파일 41분 / DKMS 9분 / 패키징 4분 / 설치 3분 |
| 쓴 디스크 | 빌드 디렉터리 14G, ccache 12G |

같은 작업의 기록이 이미 있으면 새로 만들지 않고 그 파일에 한 줄을 더한다. 조건이 달라 시간이 크게
달랐으면 그 조건을 같이 적는다 (캐시가 차 있었는지, 병렬 수).

## 안 쓰는 것

| 안 쓰는 것 | 왜 | 대신 |
|------------|-----|------|
| 진척률 추정 (`70% 쯤`) | 로그 줄 수는 진척이 아니다. 근거 없는 숫자다 | 관측된 것으로 - `"아직 컴파일 단계"` |
| 근거 없는 남은 시간 (`5분 남았습니다`) | 틀리면 그 뒤 보고를 아무도 안 믿는다 | `"얼마나 걸릴지 모른다"` |
| 안 보고 내는 중간 보고 | 실제로는 확인 안 했다는 뜻이다 | 매번 실제로 보고 낸다 |
| 예고 (`"이제 확인하겠습니다"`) | 위 경계표의 왼쪽이다 | 보고 나서 결과를 낸다 |
