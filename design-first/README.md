# design-first

**무엇을 만들지 먼저 합의하고, 승인받은 뒤에 코드를 씁니다.**

> "이런 기능 만들어줘", "여기에 붙여줘", "이렇게 바뀌게 해줘"

다른 skill 세 개는 전부 **이미 만든 것**을 다룹니다. 검증하고, 배포하고, 릴리즈합니다.
그 앞이 비어 있었습니다. 만들라고 하면 아무 절차 없이 바로 코드를 썼습니다.

## 전제

**요청 크기가 제각각입니다.** "이거 가능해?" 와 "새 수집 파이프라인 만들어줘" 에 같은 절차를 태우면
한쪽은 과하고 한쪽은 모자랍니다. 그래서 갈래를 먼저 나누고 그만큼만 합니다.

**승인 게이트는 크기와 무관합니다.** 절차의 무게는 갈래에 따라 달라지지만, 코드를 쓰기 전에
무엇을 쓸 것인지 말하고 승인받는 것은 세 갈래 모두 같습니다.

**갈래는 올라가기만 합니다.** 하다가 숨은 복잡성이 나오면 멈추고 무거운 쪽으로 갑니다.
반대로 내려오지는 않습니다.

## 갈래

| 갈래 | 언제 | 산출물 |
|------|------|--------|
| survey | "개선할 것 있나", "문제 없나" - **무엇을 고칠지가 지목 안 됐을 때** | 개선 후보 표. 고르면 갈래를 다시 판정합니다 |
| spike | "가능해?", "될까?", "대충 확인만" | 답. 만든 것은 버립니다 |
| bounded | 고칠 흐름이 **이미 repo 에 있을 때** | 대화 안의 짧은 설계 |
| architectural | 새 프로젝트·서브시스템, 남이 의존하는 계약 변경 | 설계 문서 + 계획 |

bounded 의 조건은 **"바꿀 흐름을 지금 읽을 수 있는가"** 입니다.
무슨 앱인지 아는 것으로는 부족합니다. 흐름이 없으면 bounded 가 아닙니다.

survey 는 **갈래를 정하기 위한 앞단**입니다. 무엇을 고칠지가 안 정해졌으니 갈래를 판정할 재료가 없습니다.
후보를 뽑아 표로 내고, 고르시면 그때 나머지 세 갈래 중 하나로 넘어갑니다. survey 에서 끝나지는 않습니다.

## 흐름

```
동시 세션 확인
  -> 갈래 판정 · 선언          (소리 내어 말합니다. 뒤집을 수 있게)
  -> 맥락 파악                 (바꿀 지점을 file:line 으로)
       필요하면 verify-impl     (읽어서는 안 갈리는 것만. 답을 받아 여기로 돌아옵니다)
  -> 개선 후보 표 · 선별       (survey 만. 블로킹. 고르면 갈래 판정으로 되돌아갑니다)
  -> 질문                      (답이 갈리는 것만. 지금 물을 수 있는 것을 라운드로, 추천 답과 함께)
  -> 접근 후보                 (architectural 만, 2~3개)
  -> 설계 제시 · 승인          (블로킹)
  -> 설계 문서 저장            (architectural 만, 승인 후)
  -> 구현                      (승인받은 범위만)
  -> verify-impl 로 넘김
```

## 분석이 필요할 때

**직접 읽는 것이 기본입니다.** 다만 코드를 읽어서는 안 갈리는 것들이 있습니다.

| 이럴 때 | [`verify-impl`](../verify-impl/) 로 |
|---------|------------------------------------|
| 훑을 파일이 20개를 넘음 | 팀원이 나눠 읽습니다 |
| 코드에 있는 것과 실제로 도는 것이 다를 수 있음 | 띄워보거나 붙어봐야 갈립니다 |
| 이미 되는지 안 되는지 자체가 불확실함 | 있으면 설계가 통째로 바뀝니다 |
| 운영 노드의 현재 상태가 설계 전제 | 실측이 필요합니다 |

**무엇을 알아야 설계가 갈리는지 적어서 넘깁니다.** 전수 검증을 시키는 자리가 아닙니다.
결과를 받으면 설계는 여기로 돌아와서 정합니다.

### survey 는 둘 다 돌립니다

개선 후보는 축이 둘이고, 각 축을 보는 도구가 다릅니다.

| 축 | 부를 것 | 나오는 것 |
|----|---------|-----------|
| 기능이 빠졌거나 스펙과 어긋남 | [`verify-impl`](../verify-impl/) `static` | 미구현, 미문서화, 계약 불일치 |
| 코드 자체의 결함 | `/code-review` | 버그, 중복, 비효율 |

`verify-impl` 은 코드 품질을 안 보고, `/code-review` 는 무엇이 안 만들어졌는지를 안 봅니다.
한쪽만 돌리면 그 축의 후보만 나오는데 보시기에는 그게 전부인 것처럼 보입니다.

후보 표에는 근거 `file:line`, **출처**(`verify-impl` / `/code-review` / `내 판단`),
그리고 **고치는 방법**을 한 줄씩 같이 적습니다. 출처는 도구가 낸 것과 제가 읽고 지어낸 것을
섞지 않기 위해서고, 고치는 방법은 무엇이 문제인지만 아는 표로는 고를 수가 없기 때문입니다.
**고르는 것은 사용자입니다.**

## 설계에 반드시 들어가는 것

| 항목 | 왜 |
|------|-----|
| 바꿀 지점 `file:line` | 없으면 안 읽고 설계한 것입니다 |
| 바뀐 뒤의 동작 | "좋아진다" 가 아니라 관측 가능한 형태로 |
| **안 하는 것** | 나중에 "이것도 해주는 줄 알았다" 를 막습니다 |
| 되돌리기 어려운 것 | 스키마 변경·데이터 삭제·인터페이스 변경 |
| **탈락한 후보** (survey 에서 왔을 때) | 안 적으면 다음 세션에 같은 후보를 또 뽑습니다 |
