# design-first

갈래 판정 → 맥락 파악 → 설계 제시 → **승인** → 구현 → 넘기기.

만들기 전에 무엇을 만들지 합의하는 자리다. `verify-impl`·`deploy-verify`·`release-cut` 은 전부
이미 만든 것을 다루므로, 그 앞이 비어 있었다.

## 절대 규칙

1. **승인 없이 구현하지 않는다.** 코드 작성, 파일 생성, 프로젝트 골격 만들기, 다른 구현 skill 호출이
   전부 해당한다. 절차의 무게는 일 크기에 따라 달라지지만 **승인 게이트는 크기와 무관하게 항상 있다.**
2. **갈래는 올라가기만 한다.** 하다가 숨어 있던 복잡성이 나오면 멈추고 알린 뒤 무거운 갈래로 간다.
   내려오지 않는다. 애매하면 처음부터 무거운 쪽을 고른다.
3. **갈래를 소리 내어 말한다.** "이건 bounded 로 보고 짧은 설계만 내겠습니다" 라고 먼저 말한다.
   사용자가 뒤집을 수 있어야 하기 때문이다.
4. **없는 것을 있다고 하지 않는다.** 설계에 쓰는 파일·함수·엔드포인트는 실제로 읽고 쓴다.
   `file:line` 이 없으면 "확인이 필요하다" 고 적는다. 읽어서 안 갈리면 `verify-impl` 을 부른다 (2단계).
5. **범위를 넘지 않는다.** 설계하다 눈에 띈 다른 문제는 **보고만 한다.**

## 갈래 판정

**관측 가능한 신호로 가른다.** 크기를 느낌으로 정하지 않는다.

| 갈래 | 신호 | 산출물 | 승인 대상 |
|------|------|--------|-----------|
| **survey** | **무엇을 고칠지가 지목 안 됨.** "개선할 것 있나", "문제 없나", "뭐부터 손대야 하나" | 개선 후보 표 | 어느 후보를 할지 사용자가 고름 |
| **spike** | "가능해?", "될까?", "대충 해봐", "빠르게 확인만" | 답. 만든 것은 버리는 것으로 표시 | 무엇을 시도할지 2~3문장 |
| **bounded** | 고칠 흐름이 **이 repo 에 이미 있다.** 플래그 추가, 엔드포인트 하나, 파일 하나 | 대화 안의 짧은 설계 | 그 설계 |
| **architectural** | 새 프로젝트, 새 서브시스템, 컴포넌트 간 관계나 인터페이스 변경, 남이 의존하는 계약 변경 | 설계 문서 + 구현 계획 | 설계 문서 |

**bounded 의 조건은 "고칠 흐름을 지금 읽을 수 있는가" 다.** 무슨 종류의 앱인지 아는 것으로는 부족하다.
바꿀 흐름이 repo 에 없으면 bounded 가 아니다.

**survey 는 갈래를 정하기 위한 앞단이다.** 무엇을 고칠지가 안 정해졌으니 갈래를 판정할 재료가 없다.
후보를 뽑아 사용자가 고른 뒤에 spike·bounded·architectural 중 하나로 넘어가고, 넘어간 뒤로는 그 갈래의 규칙을 그대로 따른다.
survey 에서 끝나는 일은 없다 - 고른 것이 없으면 그 자리에서 종료다.

| 이런 요청 | 갈래 | 왜 |
|-----------|------|-----|
| "이 API 에 페이지네이션 파라미터 추가" | bounded | 그 API 가 이미 있다 |
| "GPU 온도도 수집하게 해줘" | architectural | 수집 경로 자체가 없으면 새 서브시스템이다 |
| "이거 sqlite 로도 되나 확인만" | spike | 답이 필요하지 코드가 필요한 게 아니다 |
| "로그 포맷 JSON 으로" | bounded | 출력 지점이 이미 있다 |
| "다른 팀이 쓰는 응답 필드 이름 변경" | architectural | 남이 의존하는 계약이다 |
| "이 repo 에 개선할 것 있는지 봐줘" | survey | 무엇을 고칠지가 지목 안 됐다 |

## 실행 그래프

| # | 단계 | 갈래 | 게이트(통과조건) |
|---|------|------|------------------|
| 0 | 동시 세션 확인 | 전부 | 다른 세션 없음 |
| 1 | **갈래 판정 · 선언** | 전부 | 갈래를 말했고 사용자가 안 뒤집음 |
| 2 | 맥락 파악 (필요하면 `verify-impl`) | 전부 | 바꿀 흐름을 `file:line` 으로 지목 |
| 2′ | **개선 후보 표 · 선별** (블로킹) | survey | 사용자가 할 것을 고름. 고른 뒤 1 로 돌아가 갈래 재판정 |
| 3 | 질문 | bounded·architectural | 프론티어가 빔 (물을 게 남지 않음) |
| 4 | 접근 후보 제시 | architectural | 2~3개, 각각 무엇을 포기하는지 |
| 5 | **설계 제시 · 승인** (블로킹) | 전부 | 명시적 승인 |
| 6 | 설계 문서 저장 | architectural | `docs/` 에 날짜 붙여 커밋 |
| 7 | 구현 (작업 여러 개면 `plan-run`) | 전부 | 승인받은 범위만 |
| 8 | 넘기기 | 전부 | `verify-impl` 로 |

**spike 는 1 → 5 → 7 로 끝난다.** bounded 는 6을 건너뛴다.
**survey 는 1 → 2 → 2′ → 1(재판정) → 그 갈래대로 간다.** 2′ 에서 고른 것이 없으면 거기서 끝난다.

## 0. 동시 세션 확인

```sh
~/.claude/skills/shared/scripts/session-guard.sh <repo> 10
```

다른 세션이 있으면 같은 파일을 동시에 고칠 수 있다. 설계 단계에서는 읽기만 하므로 문제없지만,
7 단계 구현으로 넘어가기 전에 다시 본다.

## 1. 갈래 판정 · 선언

한 줄로 말한다. 물어보는 게 아니라 알리는 것이다. 사용자가 아니라고 하면 그쪽을 따른다.

> "이건 `/metrics` 가 이미 있으니 bounded 로 보고, 짧은 설계만 여기 적겠습니다."
> "수집 경로가 repo 에 없어서 architectural 로 봅니다. 설계 문서까지 쓰겠습니다."
> "가능한지만 물으신 것이라 spike 로 봅니다. 답만 내고 만든 것은 버리는 것으로 표시하겠습니다."
> "무엇을 고칠지가 지목 안 돼서 survey 로 봅니다. 후보를 표로 뽑아 낼 테니 고르시면 그때 갈래를 다시 판정하겠습니다."

**spike 도 선언한다.** 답만 내면 끝나는 자리라 건너뛰기 쉽지만, 사용자가 "그럼 만들어줘" 로
넘어갈 때 갈래가 이미 말해져 있어야 다음 갈래를 고를 수 있다. 다음에 할 일의 갈래를 말하는
것으로 지금 갈래 선언을 대신하지 않는다.

**애매하면 무거운 쪽이다.** 잘못 무겁게 가면 시간이 좀 들고, 잘못 가볍게 가면 다시 만든다.

**survey 에서 넘어올 때는 갈래를 다시 선언한다.** 후보 개수가 아니라 **얽힘**으로 가른다 -
고른 것이 서로 안 걸리면 bounded 여러 건이고, 한쪽을 고치면 다른 쪽이 따라 바뀌면 architectural 이다.

## 2. 맥락 파악

**바꿀 흐름을 실제로 읽는다.** 안 읽고 설계하면 없는 함수를 부르는 설계가 나온다.

```sh
rg -n "<기능 이름>" --type-add 'src:*.{go,py,ts,js}' -tsrc | head -20
git log --oneline -10 -- <관련 경로>
```

**내 기억에 없는 변경이 이미 들어가 있을 수 있다.** 남의 커밋과 지난 세션 발화(`session-grep.sh`)를 같이 본다 → `../shared/references/concurrent-sessions.md`

확인할 것.

| 무엇 | 왜 |
|------|-----|
| 바꿀 지점의 `file:line` | 없으면 bounded 가 아니다 |
| 이미 비슷한 것이 있는지 | 새로 만들기 전에 살릴 것을 먼저 본다 |
| 그 흐름을 누가 부르는지 | 바꾸면 깨지는 곳 |
| 테스트가 있는지 | 있으면 그것이 계약이다 |

### 직접 읽을지, `verify-impl` 을 부를지

**직접 읽는 것이 기본이다.** 아래 중 하나라도 걸리면 `verify-impl` 을 부른다.

| 신호 | 왜 |
|------|-----|
| 훑을 파일이 20개를 넘음 | 팀원이 나눠 읽어야 내 컨텍스트가 안 찬다 |
| **운영 노드에 붙어야 알 수 있음** | 지금 거기서 무엇이 도는지는 여기서 못 본다 |
| 확인이 명령 두세 개로 안 끝남 | 서비스를 띄우고 데이터를 넣어봐야 하는 종류다 |
| 여러 repo 에 걸침 | 계약 대조가 필요하다 |

**명령 두세 개로 끝나는 것은 직접 한다.** `nvidia-smi` 한 번, `python3 -c` 한 줄로 갈리는 것을
팀원에게 넘기면 넘기는 비용이 더 크다. 직접 돌리고 그 출력을 설계 근거로 쓴다.

부를 때 **무엇을 알아야 설계가 갈리는지** 적어서 넘긴다. 전수 검증을 시키는 자리가 아니다.
읽고 정리만 필요하면 그쪽 `static` 경로로 끝나고 접속 승인도 없다. 실행이나 접속이 필요할 때만
그쪽이 `light` 로 올리며 사람에게 묻는다.

> "`design-first` 2단계입니다. GPU 수집 경로가 이미 있는지, 있다면 실제로 값이 채워지는지만
>  확인해 주세요. 없으면 새로 만드는 설계로 갑니다."

**결과를 받으면 이 skill 로 돌아온다.** `verify-impl` 이 설계를 대신 정하지 않는다.
그쪽은 지금 무엇이 어떤지를 알려주고, 무엇을 만들지는 여기서 정해 승인받는다.

`verify-impl` 이 실노드 접속을 물으면 그 승인은 그쪽 절차대로 받는다. 설계 승인(5단계)과 별개다.

### 후보 수집 (survey 만)

**대상이 지목 안 된 개선 요청은 축이 둘이라 한쪽만 봐서는 후보가 반만 나온다.**

| 축 | 부를 것 | 나오는 것 |
|----|---------|-----------|
| 기능이 빠졌거나 스펙과 어긋남 | `verify-impl` (`static` 경로) | 미구현, 미문서화, 계약 불일치 |
| 코드 자체의 결함 | `/code-review` | 버그, 중복, 비효율 |

**둘 다 돌린다.** `verify-impl` 은 코드 품질을 안 보고(`../verify-impl/README.md:7`),
`/code-review` 는 무엇이 **안 만들어졌는지**를 안 본다. 한쪽만 돌리면 그 축의 후보만 나오는데
사용자에게는 그게 전부인 것처럼 보인다.

`static` 은 접속도 실행도 안 하므로 승인받을 것이 없다. 실측해야 갈리는 후보가 나오면
**그 후보만** `light` 로 올려 따로 묻는다. 전부를 실측으로 올리지 않는다.

## 2′. 개선 후보 표 · 선별 (survey 만, 블로킹)

**여기서 멈춘다.** 무엇을 할지는 사용자가 고른다. 내가 골라서 설계로 넘어가지 않는다.

표는 이 형식이다.

| # | 개선 후보 | 근거 `file:line` | 출처 | 드는 비용 | 안 하면 생기는 일 |
|---|-----------|------------------|------|-----------|-------------------|
| 1 | (한 줄로) | `path/file.go:120` | `verify-impl` | 파일 2개, 되돌리기 쉬움 | (관측 가능한 형태로) |

| 칸 | 어떻게 채우나 |
|----|---------------|
| 근거 | `file:line`. 없으면 후보가 아니라 **"확인 필요"** 로 적는다 |
| 출처 | `verify-impl` · `/code-review` · `내 판단` 셋 중 하나 |
| 비용 | 파일 수와 되돌리기 난이도. "쉬움/보통/어려움" 으로 뭉개지 않는다 |
| 안 하면 생기는 일 | 관측 가능한 형태로. "안 좋다" 가 아니라 "이 요청에 이 값이 온다" |

**출처를 적는 이유**는 도구가 낸 후보와 내가 코드를 읽고 지어낸 후보를 섞지 않기 위해서다.
`내 판단` 이 섞여 있으면 표 아래에 그것만 따로 짚는다. `verify-impl` 의 기준출처와 같은 취지다.

**추천은 표에 표시만 한다.** 고르는 것은 사용자다.

**후보가 없으면 없다고 말한다.** 표를 채우려고 사소한 것을 올리지 않는다.
채울 내용이 없으면 왜 없는지 말한다.

고를 것이 정해지면 **1단계로 돌아가 갈래를 다시 판정하고 선언한다.**

## 3. 질문

**답이 갈리는 것만 묻는다.** 물어서 설계가 안 바뀌면 묻지 않는다.

| 물을 것 | 안 물을 것 |
|---------|-----------|
| 두 갈래 중 어느 쪽인지 (동기/비동기, 저장/미저장) | 관례로 정해진 것 |
| 기존 동작을 바꿔도 되는지 | 이름·들여쓰기 같은 취향 |
| 어디까지가 이번 범위인지 | 내가 코드를 읽으면 알 수 있는 것 |
| 되돌리기 어려운 것을 건드리는지 | |

한 번에 묶어서 묻는다. 하나 묻고 답 듣고 또 묻지 않는다.

### 라운드로 묻는다

**지금 물어도 되는 질문 = 선행 답이 이미 나와 있어 추측 없이 물을 수 있는 것.**
그것들을 한 라운드에 다 내고 답을 기다린다. 답이 오면 새로 열린 질문이 다음 라운드다.

| 이 질문 | 이번 라운드? |
|---------|-------------|
| 다른 미결정 질문에 안 걸림 | 낸다 |
| 이번 라운드의 다른 질문 답에 걸림 | 다음 라운드로 미룬다 |
| 코드를 읽으면 갈림 | 안 묻는다. 내가 읽는다 |

**질문마다 추천 답을 붙인다.** "다 그대로" 한 마디로 라운드가 닫히게 하기 위해서다.
추천할 근거가 없으면 그 자리에 "판단 근거 없음, 정해 주세요" 라고 적는다. 억지로 채우지 않는다.

**라운드 상한은 없다.** 매 라운드가 사용자 답에서 멈추므로 끊어야 할 폭주가 없다.
대신 **bounded 인데 2라운드째 질문이 나오면 갈래를 잘못 잡은 것이다.** 규칙 2 로 올린다.

## 4. 접근 후보 (architectural 만)

2~3개를 내고 **각각 무엇을 포기하는지** 적는다. 하나만 내면 고를 수가 없다.

```
1. 폴링 - 단순하다. 지연이 주기만큼 생긴다.
2. 이벤트 훅 - 즉시 반영된다. 원본 쪽 코드를 건드려야 한다.
3. 둘 다 - 즉시성과 복구를 다 얻는다. 코드가 두 배다.
```

추천을 먼저 말하고 이유를 붙인다.

## 5. 설계 제시 · 승인 (블로킹)

**여기서 멈춘다.** 승인 전에 파일을 만들지 않는다.

갈래별로 분량이 다르다.

| 갈래 | 분량 |
|------|------|
| spike | 무엇을 시도할지 2~3문장 |
| survey | 여기 안 온다. 2′ 에서 고른 뒤 그 갈래의 분량을 따른다 |
| bounded | 대화 안에 몇 문단. 문서 파일 없음 |
| architectural | 절이 나뉜 설계. 승인 후 문서로 저장 |

설계에 반드시 들어갈 것.

- **바꿀 지점** - `file:line`
- **바뀐 뒤의 동작** - 관측 가능한 형태로. "좋아진다" 가 아니라 "이 요청에 이 응답이 온다"
- **안 하는 것** - 범위 밖으로 두는 것을 적는다. 나중에 "이것도 해주는 줄 알았다" 를 막는다
- **탈락한 후보** (survey 에서 왔을 때) - 2′ 표에서 안 고른 것을 **번호째로 전부 적는다.**
  안 적으면 다음 세션에 같은 후보를 처음부터 다시 뽑는다
- **되돌리기 어려운 것** - 스키마 변경, 데이터 삭제, 인터페이스 변경이 있으면 따로 뽑는다

## 6. 설계 문서 저장 (architectural 만)

승인받은 뒤에 저장한다. 승인 전 초안을 커밋하지 않는다.

```
docs/design/YYYY-MM-DD-<주제>.md
```

날짜를 파일명에 넣는 것은 나중에 "그때 왜 이렇게 정했나" 를 찾기 위해서다.
**결정과 그때의 근거를 같이 적는다.** 결론만 적으면 몇 달 뒤에 못 쓴다.

## 7. 구현

승인받은 범위만 한다. 하다가 설계와 다른 것이 필요해지면 **멈추고 알린다.**

| 상황 | 행동 |
|------|------|
| 설계대로 안 되는 것이 나옴 | 멈추고 무엇이 다른지 보고. 설계를 다시 승인받는다 |
| 더 나은 방법이 보임 | 보고하고 정하게 한다. 조용히 바꾸지 않는다 |
| 범위 밖 문제가 보임 | 보고만 한다 |
| 숨은 복잡성이 나옴 | 갈래를 올린다 (규칙 2) |

## 8. 넘기기

**작업이 여러 개인 계획이면 `plan-run` 으로 넘긴다.** 거기서 작업마다 팀원을 띄우고
진행을 파일에 남긴다. 작업이 하나면 여기서 끝내고 바로 다음 줄로 간다.

구현이 끝나면 동작을 확인한다. **`verify-impl` 로 간다.**
배포까지 가야 하면 그다음이 `deploy-verify` 이고, 태그가 필요하면 `release-cut` 이 먼저다.

## 하지 말 것

- 승인 없이 코드·파일 만들기
- 갈래를 말 안 하고 혼자 정하기
- 갈래를 도중에 내리기
- 바꿀 흐름을 안 읽고 설계하기
- 접근 후보를 하나만 내기
- "안 하는 것" 을 안 적기
- 승인 전 설계 초안을 커밋하기
- 설계와 다르게 구현하고 나중에 말하기
- 설계하다 눈에 띈 다른 문제를 같이 고치기
- 물어서 설계가 안 바뀌는 것을 묻기
- 아직 답 안 나온 질문에 걸린 질문을 넘겨짚어 같이 묻기
- 추천 답 없이 질문만 늘어놓기
- 개선 후보를 내가 골라서 설계로 넘어가기 (2′ 는 블로킹이다)
- 후보 축 한쪽만 돌리고 그게 전부인 것처럼 표를 내기
- 탈락한 후보를 "안 하는 것" 에 안 적기
- 실제 동작을 봐야 갈리는 것을 코드만 읽고 단정하기 (`verify-impl` 을 부른다)
- `verify-impl` 에 전수 검증을 시키고 설계 판단까지 떠넘기기
