# deploy-verify

고친 소스를 실제 노드에 반영하고, **반영됐는지 확인한 뒤 살아났는지까지** 봅니다.

> "배포해줘", "반영해줘", "이미지 복사해서 로드하고 재기동", "빌드해서 올려"

[`verify-impl`](../verify-impl/) 과 짝입니다. 이 skill 이 반영시키고 저쪽이 검증합니다.

## 전제

**전송했다는 것과 그게 돌고 있다는 것은 다른 주장입니다.**
그래서 반영 확인 없이 "배포 완료" 라고 말하지 않습니다.

**명령이 성공한 것과 서비스가 뜬 것도 다릅니다.** 재기동 후 살아났는지를 따로 봅니다.

## 흐름

```
동시 세션·원격 작업 확인
  -> 대상·범위 확인 + 브랜치·HEAD 확인
  -> 재빌드냐 파일 교체냐 판정
  -> 빌드
  -> 커밋·태그·push 승인            (블로킹)
  -> 자산 전송                       (호스트별 병렬)
  -> 로드·재기동 승인                (블로킹)
  -> 로드 + 재기동
  -> 헬스 대기
  -> 반영 확인
  -> 실증은 verify-impl 로
```

되돌리기 어려운 단계마다 게이트가 있습니다. 커밋, push, 원격 전송, 재기동, 데이터 초기화가 전부 해당합니다.

**롤백 방법을 모르면 시작하지 않습니다.** 이전 이미지 태그나 백업 위치를 먼저 확인합니다.

## 자주 나는 사고를 앞단에서 막습니다

**브랜치·HEAD 를 먼저 봅니다.** stale 한 태그나 detached 상태에서 작업했다가
한 바퀴를 통째로 버린 전례가 있습니다.

**재빌드냐 파일 교체냐를 먼저 가릅니다.**
고친 파일이 컨테이너에 마운트된 것이면 교체하고 재시작하면 끝나지만,
이미지에 컴파일되거나 COPY 된 것이면 재빌드해야 합니다.
여기서 틀리면 **옛 코드를 배포하고 그걸 검증하게 됩니다.**

**동시 세션이 있으면 커밋 방식이 달라집니다.** 경로를 명시해 add 하고, `git add -A` 를 쓰지 않습니다.
원격에서 다른 작업이 돌고 있으면 재기동하지 않고 먼저 알립니다.

## 반영 확인

전송이 끝난 것으로 판단하지 않고, 원격에서 실제로 대조합니다.

| 방법 | 어떻게 |
|------|--------|
| 내용 해시 | 로컬 `md5sum` 과 원격 `md5sum` 대조. 가장 확실합니다 |
| 이미지 태그 + 기동 시각 | `docker inspect` 로 태그와 `StartedAt` 이 방금인지 |
| 버전 엔드포인트 | 서비스가 스스로 보고하는 버전 |

## 작업 기록

배포·검증 보고에 **그 변경의 커밋 해시**를 남깁니다.
나중에 언제 무엇이 들어갔는지 추적할 수 있어야 하기 때문입니다.
