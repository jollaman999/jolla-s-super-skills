# deploy-verify

빌드 → 커밋 → 전송 → 로드 → 재기동 → 헬스 → **반영 확인** → 실증.

`verify-impl` 과 짝이다. 이 skill 이 반영시키고, `verify-impl` 이 검증한다.
수정 후 재검증이 필요하면 이 skill 을 먼저 실행하고 `verify-impl` 의 R 로 넘긴다.

## 절대 규칙

1. **되돌리기 어려운 단계마다 먼저 묻는다.** 커밋, push, 원격 전송, 재기동, 데이터 초기화가 전부 해당한다.
2. **순서를 지킨다.** 순서를 틀리면 되돌릴 수 없는 조합이 있다 (`references/order.md`).
3. **반영 확인 없이 "배포 완료" 라고 하지 않는다.** 전송했다는 것과 그게 실행되고 있다는 것은 다른 주장이다.
4. **재기동 후 살아났는지 본다.** 명령이 성공한 것과 서비스가 뜬 것은 다르다.
5. 비밀번호·토큰은 세션 안에서만. 출력에서는 마스킹.

## 실행 그래프

| # | 단계 | 의존 | 병렬군 | 게이트(통과조건) |
|---|------|------|--------|------------------|
| 0 | **동시 세션 확인** + **이전 진행 확인** | - | - | 다른 세션·원격 작업 없음. 미완 배포가 있으면 거기부터 |
| 1 | 대상·범위 확인 + **브랜치·HEAD 확인** + **대상 전체 확정** | 0 | - | 어느 호스트**들**, 무엇을, 어느 버전, 어느 브랜치 |
| 1b | **재빌드냐 파일 교체냐 판정** | 1 | - | 고친 파일이 마운트인지 이미지인지 확정 |
| 2 | 빌드 | 1 | - | exit 0. 실패하면 여기서 멈춘다 |
| 3 | **커밋·태그·push 승인** | 2 | - | 블로킹. 커밋 메시지 초안 제시 |
| 4 | 자산 전송 | 3 | ★1 호스트별 | scp 성공. 여기까지는 서비스를 안 건드린다 |
| 5 | **로드·재기동 승인** | 4 | - | 블로킹. 중단 영향 고지 |
| 6 | 로드 + 재기동 | 5 | ★1 호스트별 | 명령 exit 0 |
| 7 | 헬스 대기 | 6 | ★1 호스트별 | healthy. 상한 내 미달성이면 로그부터 |
| 8 | **반영 확인** | 7 | ★1 호스트별 | md5/이미지태그/버전 일치 |
| 9 | 실증 | 8 | - | `verify-impl` 로 넘긴다 |

★1 = 호스트별 동시. 4 를 먼저 끝내고 5 에서 승인을 받은 뒤, 6·7·8 을 호스트 하나가 이어서 처리한다.

## 0. 동시 세션 확인

배포는 되돌리기 어렵고 남에게 영향을 준다. **먼저 다른 작업이 도는지 본다.**

```sh
# 로컬: 같은 repo 에 다른 Claude 세션
~/.claude/skills/shared/scripts/session-guard.sh <repo> 10
# 원격: 그 호스트에서 실행 중인 작업
timeout 30 ssh -n root@"$H" "pgrep -af '<서비스명>|ansible|docker (build|load)|apt|yum'"
```

| 상황 | 행동 |
|------|------|
| 둘 다 없음 | 진행 |
| session-guard 가 **확인 불가(exit 2)** | 없다고 단정하지 않는다. `git add -A` 금지를 그대로 적용한다 |
| 다른 세션이 같은 repo 에 있음 | 커밋 단계에서 `git add -A` 금지. 경로를 명시해 add |
| 원격에서 다른 작업이 돎 | **재기동하지 않는다.** 사용자에게 알리고 기다릴지 묻는다 |

절차 → `../shared/references/concurrent-sessions.md`

### 이전 진행 확인 · 진행 기록

배포는 **중간에 끊기면 어디까지 갔는지 모르는 게 가장 위험하다.** 전송은 됐는데 재기동은 안 된 상태,
세 곳 중 두 곳만 나간 상태가 실제로 생긴다. `Continue from where you left off` 로 이어받은 세션이
6주 동안 16번이었다.

```sh
cat .claude/deploy-progress.md 2>/dev/null
```

| 상황 | 행동 |
|------|------|
| 파일 없음 | 새로 시작. 1단계에서 만든다 |
| 미완 단계 있음 | **어디까지 갔는지 한 줄로 알리고** 그 지점부터. 처음부터 다시 하지 않는다 |
| 전부 완료 | 결과를 요약해 보여주고 다시 돌릴지 묻는다 |

**단계가 끝날 때마다 갱신한다.** 호스트별로 어디까지 갔는지가 핵심이다.

```markdown
# 배포 진행  (갱신: 2026-08-28 14:10)
대상: app-manager v1.9.6 · 커밋 `a1b2c3d` · master
사이트 3곳 확정: 10.0.0.11(사이트A) / 10.0.1.11(사이트B) / 203.0.113.20:2002(사이트C)

| 호스트 | 전송 | 로드·재기동 | 헬스 | 반영 확인 |
|--------|------|-------------|------|-----------|
| 10.0.0.11 | 완료 | 완료 | healthy | 이미지 태그 일치 |
| 10.0.1.11 | 완료 | **미완** | - | - |
| 203.0.113.20 | 미착수 | - | - | - |

롤백: 이전 이미지 `v1.9.5`, jar 백업 `/data/backup/20260828/`
## 다음 할 일
10.0.1.11 재기동부터
```

비밀번호·토큰은 쓰지 않는다. `.gitignore` 대상이다.

## 1. 대상·범위 확인

`.claude/verify-targets.md` 가 있으면 호스트를 재질문하지 않는다.
확인할 것: 대상 호스트(들), 배포 대상(이미지/jar/tar/설정), 버전·태그, 재기동 명령, 롤백 방법.

**롤백 방법을 모르면 진행하지 않는다.** 이전 이미지 태그나 백업 위치를 먼저 확인한다.

### 대상 전체를 먼저 확정한다

한 곳만 배포하고 끝내서 **"나머지 두 곳도 배포해"** 를 다시 듣는 일이 반복됐다.
같은 제품이 여러 사이트에 나가 있으면 **몇 군데인지부터 세고 시작한다.**

```sh
cat .claude/verify-targets.md          # 사이트 목록이 여기 있다
git branch -a | grep -E 'site/|release/'   # 사이트별 브랜치가 갈려 있는지
```

| 상황 | 행동 |
|------|------|
| 사이트가 여러 곳 | **전부인지 일부인지 묻는다.** 목록을 보여주고 확정받는다 |
| 사이트별 브랜치·설정이 갈림 | 어느 브랜치로 무엇을 나가는지 사이트마다 적는다 |
| 사이트 코드가 이름에 들어감 (`agent-<site>`) | **이름을 그대로 적지 않는다.** 그 사이트 값을 먼저 조회한다 |

확정한 목록을 진행 파일에 그대로 옮긴다. 그게 "다 했는가" 의 기준이 된다.

### 브랜치·HEAD 확인 (먼저 한다)

```sh
git rev-parse --abbrev-ref HEAD    # detached 면 "HEAD"
git status --porcelain | head
git log --oneline -1
```

**작업 대상 브랜치가 맞는지 확인하고 시작한다.** stale 한 태그·detached 상태에서 작업했다가
한 바퀴를 통째로 버린 전례가 있다. 아니면 사용자에게 알리고 어느 브랜치인지 확인받는다.

## 1b. 재빌드냐 파일 교체냐

고친 파일이 **컨테이너에 마운트된 것**이면 교체+재시작으로 끝나고,
**이미지에 컴파일·COPY 된 것**이면 재빌드해야 한다. 여기서 틀리면 옛 코드를 배포하고 검증하게 된다.

```sh
docker inspect <c> --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}{{println}}{{end}}'
```

애매하면 재빌드한다. 판정표 -> `references/what-changed.md`

## 2. 빌드

프로젝트가 정한 방법을 따른다 (`Makefile`, `gradlew`, `go build`, `docker build`).
**빌드 실패는 여기서 끝이다.** 고쳐서 다시 빌드할지 사용자에게 넘긴다.

빌드 산출물의 해시를 기록한다. 8단계 반영 확인에서 쓴다.
```sh
md5sum <산출물> | cut -c1-32
```

## 3. 커밋·태그·push 승인 (블로킹)

**커밋 메시지 초안을 보여주고 승인받는다.** 자동으로 커밋하지 않는다.

- `git log --oneline -10` 으로 그 repo 의 기존 스타일을 먼저 본다
- `Co-Authored-By` 를 쓰지 않는다. 기존 스타일대로 한 줄, 핵심만
- 변경이 여러 기능에 걸쳐 있으면 **기능별로 나눠 커밋**할지 묻는다
- 태그가 필요하면 기존 태그 규칙을 확인하고 제시
- `push --force` 는 별도로 다시 묻는다

## 4. 자산 전송 [★1 호스트별]

호스트 하나 = 한 흐름. 여러 호스트면 **동시에** 진행한다. 전송까지는 서비스를 건드리지 않는다.

```sh
timeout 300 scp -o StrictHostKeyChecking=no <산출물> root@"$H":/data/docker/
```

`ssh -n` 과 `timeout` 은 필수다. 없으면 `ssh` 가 stdin 을 읽어 버려서 호출한 스크립트의 남은 줄이 실행되지 않는다.

## 5. 로드·재기동 승인 (블로킹)

재기동 전에 **영향을 구체적으로 알린다.**

> 10.0.0.11 의 app-svc 를 재기동합니다.
> 영향: 재기동 중 수집 중단 약 20초
> 롤백: 실패 시 이전 이미지 v1.5.0 으로 되돌립니다
> 진행할까요?

운영 호스트가 여러 대면 **한 대씩 할지 동시에 할지 묻는다.** 전부 동시에 내리면 서비스가 통째로 끊긴다.

## 6·7·8. 로드 · 재기동 · 헬스 · 반영 확인 [★1 호스트별]

승인이 난 뒤에만 여기로 온다. 호스트 하나가 넷을 이어서 처리한다.

```sh
# 6. 로드 + 재기동
timeout 400 ssh -n -o StrictHostKeyChecking=no root@"$H" \
  "docker load -i /data/docker/<이미지>.tar && bash /data/scripts/run_<svc>.sh"
# 7. 헬스 대기
~/.claude/skills/deploy-verify/scripts/deploy-wait.sh "$H" <컨테이너> 120
# 8. 반영 확인
timeout 60 ssh -n root@"$H" "md5sum /data/docker/<산출물> | cut -c1-32"   # 로컬 해시와 대조
timeout 60 ssh -n root@"$H" "docker inspect <svc> --format '{{.Config.Image}} {{.State.StartedAt}}'"
```

레시피 → `references/deploy.md`

### 헬스가 안 뜨면

**로그를 먼저 본다.** 재시도부터 하지 않는다.
```sh
timeout 60 ssh -n root@"$H" "docker logs --tail 80 --since 5m <svc> 2>&1"
```
상한 내에 안 뜨면 멈추고 사용자에게 보고한다. 롤백할지 묻는다.

### 반영 확인 - 가장 자주 놓치는 단계

"고쳤는데 반영이 안 된" 상황이 여기서 걸린다. 셋 중 최소 하나로 확인한다:

| 방법 | 명령 |
|------|------|
| 파일 해시 | 로컬 `md5sum` vs 원격 `md5sum` |
| 이미지 | `docker inspect --format '{{.Config.Image}}'` + `StartedAt` 이 방금인지 |
| 버전 | `<bin> --version`, `/actuator/info`, `/version` 엔드포인트 |

**mtime 을 단독 근거로 쓰지 않는다.** 재현성 빌드(`--mtime=@0`)가 타임스탬프를 죽여서
새 바이너리를 풀어도 mtime 이 1970 그대로다. 실제로 이 때문에 배포하고도 타깃 버전이 옛 값에 고정된 적이 있다.
mtime 을 쓰려면 size 나 TTL 로 보강한다. 상세 -> `references/what-changed.md`

**불일치면 실증(9)으로 넘어가지 않는다.** 옛 바이너리를 검증하고 pass 판정하는 게 최악이다.

## 커밋 해시 기록

배포·검증 보고서에 **그 변경의 커밋 해시**를 남긴다. 나중에 "언제 뭐가 들어갔나" 를 추적할 수 있다.
기존 프로젝트 메모리가 전부 이 방식이다 (`커밋 2df2690e1 master`, `커밋 36b6443a8` 등).

```sh
git log --oneline -1        # 배포한 커밋
git rev-parse --short HEAD
```

## 9. 실증

여기서 끝내지 않는다. `verify-impl` 로 넘겨 실제로 동작하는지 본다.
사용자가 기대 상태를 말했으면 (`"8086 influxdb에서 svc-nfs랑 svc-web 수집되는지"`) 그게 그대로 검증 항목이다.

## 하지 말 것

- 승인 없이 커밋·push·재기동
- 롤백 방법을 모른 채 배포
- 반영 확인 없이 "배포 완료" 라고 말하기
- 헬스 안 뜨는데 로그 안 보고 재시도
- 운영 호스트 전체를 동시에 재기동 (묻고 한다)
- 순서 뒤집기 (재설치 전에 데이터 초기화 등)
- `timeout` / `ssh -n` 없는 원격 명령
- 빌드 실패를 넘어가서 옛 산출물 배포
- **동시 세션·원격 작업 확인 없이 배포**
- 동시 세션이 있는데 `git add -A`
- **브랜치 확인 없이 배포** (stale 태그·detached 에서 작업한 전례)
- **재빌드가 필요한데 파일만 교체**하고 반영됐다고 보고
- **mtime 만 보고 반영 확인** (재현성 빌드는 mtime 이 1970 이다)
- 배포 보고에 커밋 해시를 안 남기기
- **대상이 몇 군데인지 확정 안 하고 한 곳만 배포하고 끝내기**
- **진행 기록 없이 여러 호스트 배포 시작** (끊기면 어디까지 갔는지 모른다)
- 사이트 코드가 들어간 이름을 그대로 옮겨 쓰기 (`agent-demo` 를 다른 사이트에서 그대로 쓰기)
- 연동 repo 반영 확인을 빼먹기 (`../shared/references/downstream.md`)
