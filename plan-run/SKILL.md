# plan-run

재개 확인 → 계획 읽기 → **작업 루프**(구현 → 검토 → 커밋 → 진행 갱신) → 마무리 → 넘기기.

`design-first` 의 architectural 갈래가 계획서를 만들고 여기로 넘어온다. 계획서가 없으면 이 skill 이 아니다.

## 절대 규칙

1. **진행을 파일에 적는다.** 대화 기억은 컨텍스트가 압축되면 사라진다. 자기 위치를 잃고
   **이미 끝난 작업을 처음부터 다시 하는 것**이 가장 비싼 실패다. 작업이 끝날 때마다 파일을 갱신한다.
2. **계획에 없는 것을 하지 않는다.** 하다가 필요해지면 멈추고 알린다. 조용히 범위를 넓히지 않는다.
3. **작업 하나가 끝나야 다음으로 간다.** 구현만 해놓고 다음 작업으로 넘어가지 않는다.
   검토와 커밋까지가 한 작업이다.
4. **검증 없이 완료로 적지 않는다.** 무엇을 돌려서 무엇을 봤는지가 진행 파일에 남아야 한다.
5. **되돌리기 어려운 작업은 그 작업 차례에 따로 묻는다.** 계획 승인이 개별 승인을 대신하지 않는다.

## 실행 그래프

| # | 단계 | 담당 | 게이트(통과조건) |
|---|------|------|------------------|
| S | 동시 세션 확인 | 팀장 | 다른 세션 없음 |
| N | **이전 진행 확인 · 재개** | 팀장 | 진행 파일 있으면 이어서 |
| P | 계획 읽기 · 작업 쪼개기 | 팀장 | 작업마다 완료 조건이 관측 가능 |
| Q | **작업 순서 · 위험 항목 확인** (블로킹) | 팀장 | 순서와 위험 항목을 사용자가 확인 |
| T | **작업 루프** | `plan-implementer` × 작업 | 작업마다 검토 통과 + 커밋 |
| R | 작업 검토 | `plan-reviewer` × 작업 | 계획 대조 통과 |
| G | 마무리 보고 | 팀장 | 한 작업도 빠짐없이 상태가 적힘 |
| V | 넘기기 | 팀장 | `verify-impl` 로 |

**팀장이 하는 것:** 계획 해석, 작업 쪼개기, 순서 판단, 사람과의 대화, 종합.
**팀장이 하지 않는 것:** 작업 하나를 직접 구현하기. 작업마다 새 팀원을 띄운다.

## S. 동시 세션 확인

```sh
~/.claude/skills/shared/scripts/session-guard.sh <repo> 10
```

여러 작업을 연달아 커밋하므로 남의 미커밋 변경이 섞이기 쉽다.
있으면 `git add -A` 를 쓰지 않고 경로를 지정해 커밋한다.

## N. 이전 진행 확인 · 재개

**시작 전에 `.claude/plan-progress.md` 를 먼저 본다.**

| 상황 | 행동 |
|------|------|
| 파일 없음 | 새로 시작 |
| 파일 있고 미완 작업 있음 | **어디까지 했는지 한 줄로 알리고** 그 작업부터 이어간다 |
| 파일 있고 전부 완료 | 요약을 보여주고 "마무리할까요" 를 묻는다 |
| 사용자가 "어디까지 했냐" 를 물음 | 파일을 읽어 바로 답한다. 다시 실행하지 않는다 |

**진행 파일은 작업이 끝날 때마다 갱신한다.** 팀원이 돌아올 때마다가 아니라 작업 단위다.

```markdown
# 계획 진행  (갱신: 2026-09-04 14:20)
계획: docs/design/2026-09-04-node-alert.md · 대상: <repo> · 브랜치: feat/node-alert

| # | 작업 | 상태 | 커밋 | 검증 |
|---|------|------|------|------|
| 1 | 임계치 설정 스키마 | 완료 | a1b2c3d | 단위 3건 통과 |
| 2 | 판정 로직 | 완료 | e4f5g6h | 경계값 5건 통과 |
| 3 | 슬랙 전송 | **진행중** | | |
| 4 | 이력 저장 | 대기 | | |
| 5 | 조회 API | 대기 | | |

## 결정
- 3번: 재시도는 3회 고정. 지수 백오프는 이번 범위 밖 (사용자 확인 2026-09-04)

## 범위 밖 발견
- `app/db.py:3` DB_PATH 가 상대경로라 cwd 에 따라 다른 파일을 연다. 보고만 함
```

**비밀번호·토큰은 진행 파일에 쓰지 않는다.**

## P. 계획 읽기 · 작업 쪼개기

계획서를 읽고 작업으로 자른다. **자르는 기준은 "그것만 되돌려도 말이 되는가" 다.**

| 작업 하나에 있어야 하는 것 | 없으면 |
|----------------------------|--------|
| 무엇을 만드는지 | 팀원이 다르게 만든다 |
| **관측 가능한 완료 조건** | 됐는지 아무도 모른다 |
| 어느 파일을 건드리는지 | 작업끼리 같은 파일을 밟는다 |
| 앞선 어느 작업에 의존하는지 | 순서가 틀린다 |

완료 조건이 "잘 동작한다" 처럼 관측 불가능하면 **거기서 멈추고 묻는다.** 지어내지 않는다.

작업이 서로 같은 파일을 건드리면 **순차로 간다.** 동시에 띄우지 않는다.

## Q. 작업 순서 · 위험 항목 확인 (블로킹)

표로 내고 확인받는다. **되돌리기 어려운 작업을 미리 짚어서 같이 묻는다.**

| # | 작업 | 완료 조건 | 의존 | 위험 |
|---|------|-----------|------|------|
| 1 | 임계치 설정 스키마 | 설정 파일 로드 시 잘못된 값이 거부됨 | - | 안전 |
| 4 | 이력 저장 | 알림 1건 후 행 1개 증가 | 2 | **위험** (스키마 변경) |

사용자가 순서를 바꾸거나 작업을 빼면 그대로 따른다.

## T. 작업 루프

작업마다 **새 팀원을 띄운다.** 팀장이 직접 구현하지 않는다.

```
plan-implementer  ->  plan-reviewer  ->  커밋  ->  진행 파일 갱신  ->  다음 작업
```

팀원에게 넘길 것.

| 넘길 것 | 왜 |
|---------|-----|
| 그 작업 하나의 설명과 완료 조건 | 범위를 넘지 않게 |
| 계획서 경로 | 맥락이 필요하면 읽으라고 |
| 건드릴 파일 목록 | 다른 작업 구역을 밟지 않게 |
| 앞 작업이 만든 것 중 쓸 것 | 다시 만들지 않게 |

**대화 기록을 통째로 넘기지 않는다.** 팀원은 컨텍스트가 격리돼 있어야 값을 한다.

작업이 서로 독립이고 3개 이상이면 **한 메시지에서 동시에 띄운다.** 같은 파일을 건드리면 순차다.

### 검토에서 걸리면

| 라운드 | 행동 |
|--------|------|
| 1~2 | 같은 팀원에게 지적 사항을 주고 고치게 한다 |
| 3 | 새 팀원을 띄운다. 앞 팀원이 못 보는 것이 있다 |
| 4 | 멈추고 사용자에게 넘긴다. 계획이 틀렸을 수 있다 |

**상한 없이 반복하지 않는다.**

### 계획과 다른 것이 나오면

| 상황 | 행동 |
|------|------|
| 계획대로 하면 안 되는 것이 확인됨 | 멈추고 무엇이 다른지 보고. 계획을 고쳐 다시 승인받는다 |
| 더 나은 방법이 보임 | 보고하고 정하게 한다 |
| 범위 밖 문제가 보임 | 진행 파일 "범위 밖 발견" 에 적고 계속한다 |
| 작업이 예상보다 큼 | 쪼개서 다시 확인받는다 |

## R. 작업 검토

`plan-reviewer` 가 **계획서와 실제 변경을 대조한다.** 코드 품질은 `/code-review` 몫이다.

검토가 보는 것.

- 계획의 완료 조건이 실제로 충족됐는가. 무엇을 돌려서 봤는가
- 계획에 없는 변경이 섞였는가
- 앞 작업이 만든 것을 부수지 않았는가

## G. 마무리 보고

**작업 하나도 빠짐없이 상태가 적혀야 한다.** 못 한 것은 못 했다고 적는다.

| # | 작업 | 상태 | 커밋 | 근거 |
|---|------|------|------|------|

- 계획에서 뺀 작업과 그 이유
- 범위 밖 발견 (보고만 한 것)
- 남은 위험

## V. 넘기기

구현이 끝났다고 동작하는 것은 아니다. **`verify-impl` 로 넘긴다.**
배포까지 가면 `deploy-verify`, 태그가 필요하면 `release-cut` 이 먼저다.

## 하지 말 것

- 계획서 없이 시작하기
- 진행 파일을 안 만들거나 작업 끝나고 안 갱신하기
- 팀장이 작업을 직접 구현하기
- 대화 기록을 통째로 팀원에게 넘기기
- 완료 조건이 관측 불가능한 채로 작업 시작하기
- 검토 없이 다음 작업으로 넘어가기
- 검토 지적을 상한 없이 반복해서 고치기
- 계획과 다르게 구현하고 나중에 말하기
- 되돌리기 어려운 작업을 계획 승인만 믿고 실행하기
- 같은 파일을 건드리는 작업을 동시에 띄우기
- 구현 끝났다고 동작한다고 보고하기
