# 내가 틀렸던 방식

`silent-failure.md` 는 **코드가** 조용히 틀리는 양식이고, 이건 **내가** 조용히 틀리는 양식이다.
6주치 세션에서 사용자가 내 판정에 이의를 단 지점을 추려 낸 것이다. 전부 실제로 내가 틀렸던 건이다.

`verify-refuter` 는 pass 항목마다 이 목록을 반증 각도로 쓴다.

## 1. 계산해서 만든 값을 실측이라고 부른다

**가장 위험하다.** 판정의 근거 자체가 가짜가 되는데, 표에 숫자가 있으니 실측처럼 보인다.

> 내가 쓴 것: "**실측했습니다.** ECC 오버헤드 3084 MiB"
> 사용자: "그건 니 추정 아니야?"
> 다음 턴의 나: "**정정합니다. 3084 은 실측이 아닙니다.** 49152 는 측정한 값이 아닙니다"

`3084 = 49152(카탈로그 스펙) - 46068(실측)` 이었다. **뺄셈이 한 번이라도 들어가면 실측이 아니다.**

evidence 에 적을 때 갈라 놓는다.

```
읽은 값 : FB Total 46068 MiB      (nvidia-smi -q, 원문 그대로)
파생값  : 3084 = 49152 - 46068    (49152 는 카탈로그 값이지 측정값이 아님)
```

단위·자릿수도 같이 확인한다. 그때 `MiB` 를 `MB` 로 섞어 쓴 것도 같이 지적받았다.

## 2. 고쳤는데 그 코드 경로가 그 환경에서 안 탄다

배포 반영 확인(`md5`·이미지 태그)은 통과한다. **파일은 갔는데 조건이 안 맞아 코드가 실행되지 않는다.**

> 내가 쓴 것: "커밋·push 완료. 배포하면 다음 주기에 자가 교정됩니다. 확인만 하시면 됩니다"
> 사용자: "스크립트 실행할때 **여전히** bare_metal 로 나오는데"
> 다음 턴의 나: "**그래서 그 환경에서 안 먹혔습니다.** 그 GPU 2·3번은 이 세 신호가 다 없었던 겁니다"

기존 게이트를 그대로 둔 채 우회 경로만 하나 더 붙였는데, 그 환경에는 그 신호가 없었다.

**수정이 조건 분기 안에 들어갔으면 그 조건이 대상 환경에서 참인지를 따로 본다.**
반영 확인과 별개 항목이다.

```sh
# 고친 함수가 실제로 불렸는가 - 로그·표식·카운터 중 하나
timeout 60 ssh -n root@"$H" "grep -c '<새로 넣은 로그 문구>' <로그> ; <스크립트> --dry-run 2>&1 | head"
```

## 3. 사용자가 이상하다고 한 것을 코드 논증으로 눌러 pass

> 내가 쓴 것: "동작을 끝까지 추적했습니다. **기능적 버그는 없습니다.**" (게이트가 규칙과 일치함을 표로 증명)
> 사용자: "`2f5bd9e...` 여기서 뭔가 잘못 고친거 같은데 pull 받아서 다시 봐봐"

**사용자 신고는 관측이고 코드 논증은 추론이다.** 추론으로 관측을 기각하지 않는다.
코드가 규칙과 일치한다는 증명은 "이 코드가 그 규칙을 구현한다" 는 뜻이지 "사용자가 본 화면이 정상이다" 가 아니다.

사용자가 이상을 신고한 항목은 **최소한 그 사람이 본 경로로 한 번 재현**한 뒤에 판정한다.
재현이 안 되면 `pass` 가 아니라 `unknown` + "재현 안 됨" 이다.

## 4. 관측하지 않은 최대치를 산술로 단정

> 내가 쓴 것: "4개 다 온전히 12GB 받습니다 ... **동시 구동 가능 개수는 3개입니다**"
> 같은 글 안에: "실제로 2개만 켜져 있어 문제가 안 드러난 상태입니다"
> 사용자: "진짜야? 인터넷 뒤져서 실제로도 그런지 확인해봐"

2개를 보고 4개일 때를 나눗셈으로 답했다. `boundary.md` 의 "N개" 를 짚기는 했는데 **짚고 나서 추정으로 메웠다.**

관측 범위 밖의 수치는 값을 내지 말고 **관측 범위를 같이 적는다.**

> 2개 동시 구동은 확인했다(각 12288 MiB 온전히 할당). 3개 이상은 **안 해 봤다.**
> 총량 46068 로는 3개가 상한으로 보이지만 이건 산술이지 관측이 아니다.

## 5. 내가 확인한 항목이 사용자가 보는 것과 다르다

> 내가 쓴 것: "끝났습니다 ... iframe URL·CSP 차단 없음" (검증 로그까지 첨부)
> 사용자: (스크린샷) "**아직 위에 나오자나**"

CSP 도 iframe URL 도 전부 통과했다. 사용자가 본 건 **화면 위쪽에 남아 있는 상단바**였다.
내가 고른 확인 항목이 통과했다는 것과 요청이 충족됐다는 것은 다른 주장이다.

프론트 항목은 **사용자가 말한 문장을 그대로 판정기준으로 쓴다.** "상단바가 안 보이면 돼" 가 기준이면
기준은 상단바의 가시성이지 CSP 헤더가 아니다. 화면 확인이 필요하면 그렇다고 말하고 스크린샷을 요청한다.

## 6. 원인을 하나로 좁히면서 배제 못 한 후보를 안 적는다

> 내가 쓴 것: "이유가 명확합니다. **웜 리부트는 PSU 를 끄지 않습니다** ... 재부팅 전부터 이미 빠져 있었습니다"
> 사용자: "커널 업데이트 된건 아니지? **지난번에 커널업데이트 되고서 안잡히던데**"

"재부팅 전부터 빠져 있었다" 까지가 내가 확인한 전부였고, **왜 빠졌는지는 모르는 상태**였다.
그런데 문장은 원인을 확정한 것처럼 읽혔다.

원인을 하나로 지목할 때는 **배제한 후보와 배제 근거**, **배제하지 못한 후보**를 같이 적는다.
`H` 의 `confidence: low` 가 이 자리다.

## 7. 재현 경로를 안 물어보고 코드에서 그럴듯한 경로를 찾는다

> 내가 쓴 것: "원인 - `SITE_CODE` 는 치환 안 된 플레이스홀더" (양쪽 repo 수정 push 완료)
> 사용자: "**그걸 말한게 아닌데** site code 는 항상 설정되어 있자나 ... 요청할때 뭔가 그런거 같은데"

코드에서 그 증상을 낼 수 있는 경로를 찾아내긴 했다. 그런데 **사용자가 겪은 경로가 아니었다.**
증상을 낼 수 있는 경로가 둘 이상이면, 어느 쪽인지는 코드가 아니라 **그 사람이 한 조작**이 정한다.

수정을 먼저 밀지 말고 **어떤 조작에서 났는지 한 줄 묻는다.** `D` 의 입력 우선순위와 같은 이유다.

## pass 를 적기 전에 스스로 묻는 것

| 물음 | 아니면 |
|------|--------|
| 이 숫자는 읽은 값인가, 만든 값인가 | 파생값이라고 표시 |
| 고친 코드가 그 환경에서 실제로 탔는가 | `unknown` |
| 사용자가 본 경로로 재현했는가 | `unknown` + "재현 안 됨" |
| 이 수치는 관측 범위 안인가 | 범위를 같이 적기 |
| 내가 본 항목이 사용자가 말한 그것인가 | 기준을 사용자 문장으로 되돌리기 |
| 배제 못 한 원인 후보가 있는가 | 같이 적기 |
| 어떤 조작에서 났는지 물어봤는가 | 코드에서 찾은 경로를 원인으로 확정하지 않기 |
