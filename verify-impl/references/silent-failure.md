# 무음 실패 - 검증이 실제로 잡아야 하는 것

## 왜 1순위인가

관측 시스템 계열 코드베이스의 **지배적 실패 양식은 예외가 아니라 무음 실패**다.
예외를 안 던지고 **조용히 틀린 값을 낸다.** 200 이 오고 화면에 숫자가 뜨는데 그 숫자가 틀렸다.

그래서 **"에러가 없다" 는 pass 의 근거가 아니다.** 기대한 동작의 흔적이 관측돼야 pass 다.

## 실제로 관측된 무음 실패 유형

| 유형 | 어떻게 조용히 틀리나 | 확인 방법 |
|------|----------------------|-----------|
| **정규식 치환 no-op** | 패턴이 안 맞아 치환이 0건인데 그대로 진행 | 치환 전후 값을 둘 다 찍어 비교 |
| **alias 를 못 찾아 인덱스 추측** | 컬럼 순서로 때려맞춰 다른 필드를 반환 | 필드명과 값을 같이 확인 |
| **파싱 실패 시 기본값 폴백** | 0 이나 빈 문자열이 정상값처럼 흘러감 | 0/빈값이 "없음" 인지 "진짜 0" 인지 구분 |
| **필드 타입 충돌로 write 거부** | 저장 단계에서 400 인데 수집은 정상으로 보임 | 저장소에서 되읽어 확인 |
| **빈 태그 값** | `instance=` 같은 빈 태그로 파싱 에러 | 저장 단계까지 따라감 |
| **응답 필드명 오탈자** | 프론트가 없는 필드를 읽어 `undefined` -> 화면에 `-`. 예외 없음 | 백엔드 응답 클래스 필드와 글자 단위 대조 |
| **목이 프론트 기대에 맞춰짐** | 목 모드에선 정상, 실서버에서만 깨짐 | 목을 검증 근거로 쓰지 않는다 |
| **안 받는 파라미터를 보냄** | 프레임워크가 조용히 버림. 기본값으로 동작 | 백엔드 핸들러 시그니처와 대조 |
| **조회 필터 불일치** | `cpu='cpu-total'` 로 거르는데 데이터는 `instance-total` → 결과 null | 필터 없이도 조회해 데이터 존재 여부 확인 |
| **uuid/키 불일치** | 조회키와 저장키가 달라 조용히 빈 결과 | 저장된 실제 키를 눈으로 확인 |
| **stale 설정으로 기능 미발동** | 조건이 안 맞아 코드가 아예 안 탐 | 그 코드가 실행됐다는 증거를 찾음 |

## 체크리스트 판정기준을 쓸 때

**금지되는 판정기준** (전부 무음 실패를 통과시킨다):

```
"에러 없이 응답"        <- 틀린 값도 에러 없이 온다
"200 이면 pass"         <- 빈 배열도 200 이다
"화면에 표시됨"          <- 0 이나 N/A 도 표시된다
"로그에 에러 없음"       <- 안 탄 코드는 로그도 안 남긴다
```

**대신 이렇게 쓴다:**

```
"200 이고 items 길이 >= 1 이고 각 item 에 gpu_uuid 가 있음"
"저장소에서 되읽었을 때 방금 쓴 값과 같음"
"해당 코드 경로가 실행됐다는 증거(로그 라인/카운터/타임스탬프)가 있음"
"값이 0 이면, 진짜 0 인지 수집 실패인지를 다른 경로로 교차 확인"
```

## 값이 나왔을 때 한 번 더 의심할 것

- **0 / N/A / 빈 배열이 정상인가?** 대부분은 수집 실패의 위장이다.
- **이 값이 어제와 같은가?** 고정 응답·캐시일 수 있다.
- **다른 경로로 같은 값이 나오나?** API 와 DB 를 둘 다 본다.
- **내가 방금 고친 코드가 실제로 탔나?** 배포 반영과 조건 분기를 확인한다.
