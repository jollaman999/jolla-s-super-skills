# hunt - repo 전체에서 결함 찾기

"보안 취약점 있는지", "락 문제 없는지", "버그 날 곳 없는지" 처럼 **지금 코드에 숨은 결함을 찾아 달라는** 요청의 기법이다.
무엇을 확인할지 나열한 점검표가 아니다. **어떻게 찾고, 어떻게 확정하고, 어떻게 고르는지**를 적는다.
언어를 가리지 않는다. 사례에 나오는 명령은 그 세션이 Go 라서 Go 로 쓴 것이다.

사례는 전부 한 세션(tunnel-manager, 2026-11-21~22)에서 실제로 있었던 일이다.

| 자리 | 부를 것 |
|------|---------|
| 변경분(이 PR·방금 고친 것) | `/code-review` |
| 바깥의 CVE·새 버전이 우리에게 걸리는지 | `upstream` 경로 |
| 지금 코드 전체·한 영역의 결함 | **이 경로** |

---

## 1. 찾기

### 1.1 갈래를 나눠 동시에 맡긴다

보안 / 락·동시성 / 성능·일반 버그를 **세 팀원에게 따로** 한 메시지에서 맡긴다 (`hunt-security`, `hunt-concurrency`, `hunt-perf`).

- 갈래마다 따라가는 길이 다르다. 보안은 입력이 어디까지 흘러가는지, 락은 두 실행 흐름이 어떻게 엇갈리는지, 성능은 무엇이 규모에 비례하는지를 본다.
- 한 명이 다 보면 처음 잡은 갈래로 쏠린다. 나누면 각자 끝까지 따라갈 시간이 생긴다.
- 각 팀원에게 **다른 갈래는 남이 본다**고 알린다. 겹쳐 파면 같은 발견이 세 번 온다.

넘길 것: repo 경로, HEAD, 규모(줄 수·패키지), 부하 가정(한 사람이 쓰는 단일 프로세스인지, 동시 요청이 많은 서버인지), 이전 작업 기록 경로.

### 1.2 발견마다 확신도를 가른다

| 칸 | 내용 |
|----|------|
| 위치 | `file:line`. 락 문제는 **락을 잡는 곳과 문제가 나는 곳 둘 다** |
| 시나리오 | "이 입력·이 상태 → 이 결과". 락은 실행 순서로: "A 가 X 를 쥔 채 Y 를 기다리는 동안 B 가 …" |
| 심각도 | high / medium / low |
| 확신도 | `confirmed`: 호출 경로를 끝까지 따라가 봤다. `plausible`: 중간에 가정이 있다. **무엇을 가정했는지 적는다** |

plausible 을 confirmed 로 올리는 것은 재현이다 (2절). 코드를 더 읽어서 올리지 않는다.

### 1.3 "확인했지만 문제 없던 것" 을 같이 받는다

발견 목록만 받으면 **무엇을 봤는데 괜찮았는지**와 **아예 안 본 것**이 구별되지 않는다.

- 상위 미들웨어·검증 함수가 이미 막는 것은 끝까지 따라가 보고 **이 목록으로 뺀다.** 그럴듯한 오탐이 여기서 걸러진다.
- 다음 회차가 같은 곳을 다시 파지 않는다.

> 사례: 보안 팀원이 인코딩된 경로로 인증 미들웨어를 우회하는 요청(`/api/%6cogin`)을 실제로 보내 봤다.
> 라우터가 404 로 떨어뜨려 우회가 아니었다. CSRF, XSS(`innerHTML` 0건, rg 종료 코드 1), 비밀값 응답 노출 등 13가지가 이 목록으로 갔다.

### 1.4 도구 결과는 닿는지 판정한 뒤 쓴다

정적 분석기·취약점 스캐너·린터가 낸 것을 그대로 옮기지 않는다. **그 코드에 실제로 입력이 닿는지** 따라가 본다.

> 사례: gosec 45건 중 열린 리다이렉트와 정수 변환 2건을 직접 따라갔고, 둘 다 실제로는 문제가 아니었다.
> 나머지는 의도된 패턴이었다.

### 1.5 도구가 비었으면 왜 비었는지 본다

**에러로 끝난 도구는 "문제 없음" 이 아니라 "결과 없음" 이다.**

| 함정 | 사례 |
|------|------|
| 분석기가 대상 언어 버전보다 오래됨 | staticcheck 바이너리가 go1.23 으로 빌드돼 go1.26 이상을 요구하는 모듈을 분석하지 못하고 에러로 끝났다. 분석기를 지금 툴체인으로 다시 설치하자 9건이 나왔다 |
| 스캐너가 로컬 툴체인 기준으로 본다 | govulncheck 가 로컬 Go 1.27.3 의 표준 라이브러리 취약점(GO-2026-6859)을 잡았다. 실제 빌드가 쓰는 툴체인을 고정하자 0건. 스캐너가 본 툴체인과 배포 빌드가 쓰는 툴체인을 맞춰서 본다 |
| 긴 검사가 시간 초과 | 경쟁 조건 검사(`-race`)가 큰 패키지에서 580초에 끊겼다. 검사 없이 돌리니 62초에 통과해 멈춘 것이 아니라 느린 것이었다. 나눠 돌려 전부 0건을 확인했다 |

빈 검색도 같다. 검색이 그 범위를 다 훑었을 때만 "없다" 다 (CLAUDE.md "추정을 사실로 말하지 않기").

### 1.6 성능은 숫자로 잰다

"느릴 수 있다" 로 올리지 않는다. 한 번을 재고, 규모를 곱한 값에는 **추정이라고 적는다.**

> 사례: 비밀번호 걸린 SSH 키 해독 1회를 재니 KDF 16라운드에서 102ms, 100라운드에서 626ms 였다.
> "Host 10대 × 포트 10개면 첫 reconcile 에 약 63초(추정), 그동안 전역 락을 쥔다" 로 올렸다.

핫패스가 아닌 곳의 미세 최적화는 올리지 않는다.

### 1.7 이전 기록은 단서다

지난 분석·작업 기록(`.claude/plan-progress-*.md` 등)을 넘기되, 사실로 쓰지 않는다.

- 줄 번호는 그새 어긋났다. **지금 HEAD 에서 다시 찾는다.**
- `git log` 로 최근 커밋이 이미 고쳤는지 본다.

## 2. 확정하기

**재현되지 않은 결함은 고치지 않는다.** 재현이 안 되면 결과만 보고한다.
"고쳤다" 는 원래 증상이 다시 안 나는 것이고, "회귀 없음" 은 고치기 전후를 같은 조건으로 돌린 결과다.

### 2.1 고치기 전 코드를 따로 꺼낸다

```sh
git worktree add --detach <scratchpad>/before <고치기 전 커밋>
```

같은 재현 테스트를 고치기 전과 후에서 돌린다. `git stash` 로 오가지 않는다.
끝나면 `git worktree remove` 로 지운다.

### 2.2 재현은 고치기 전 코드에서 **매번** 실패해야 한다

가끔만 실패하는 재현 테스트는 버그를 놓친다. 고치기 전에도 통과하는 회차가 있으면 고친 뒤 통과가 아무 뜻이 없다.
**고치기 전 실패율을 잰다.** 매번이 아니면 버그가 드러나는 조건을 고정한다.

> 사례: jump 연결을 닫다가 락이 묶이는 버그의 첫 재현 테스트가 고치기 전 코드에서도 가끔 통과했다.
> 송신 버퍼가 스스로 커지면 쓰기가 다른 곳에서 멈춰, 버그가 드러나는 상태가 만들어지지 않았다.
> 송신 버퍼를 4KB 로 고정하자 고치기 전 20/20 실패, 고친 뒤 120/120 통과.

### 2.3 동시성 버그는 동시에 보낸다

- 두 요청을 동시에 N번 보낸다. 한 번 통과로 끝내지 않는다.
- 락을 오래 쥐는 문제는 **그동안 다른 요청이 기다린 시간**으로 잰다.

> 사례: 설정 저장 두 건을 동시에 보내니 고치기 전 첫 회에 한쪽 변경이 사라졌다. 고친 뒤 50회 × 3번(`-race` 포함) 통과.
> 키를 해독하는 동안 상태 API 가 기다린 시간: 102ms → 0.16ms. 트랜잭션 안 해독: 다른 쿼리 지연 99ms → 0.4ms.

### 2.4 죽는 버그는 실제 바이너리로 죽여 본다

계산으로 "넘쳐서 패닉 날 것" 은 plausible 이다. 그 상태를 만들어 띄운다.

> 사례: 주기 설정에 1e10 을 저장한 DB 로 실제 바이너리를 띄우니 `panic: non-positive interval for NewTicker` 로 시작하자마자 죽었다.
> 고친 뒤 같은 DB 로 띄워 정상 기동과 보정 로그 2줄을 봤다.

### 2.5 보안 수정은 돌아가는 길로 다시 공격한다

막은 요청 하나가 거부되는 것으로 끝내지 않는다.

- 표기만 바꾼 같은 요청: 대소문자, IPv6 표기, 순서만 바꾸기, 다른 필드를 같이 보내기
- **같은 상태를 바꾸는 다른 경로**를 전부 찾는다: 다른 API, 가져오기(import), 일괄 처리

> 사례: Host 주소를 바꿀 때 계정 비밀번호를 요구하게 고친 뒤 대문자 주소, IPv6 표기 바꾸기, jump 순서만 바꾸기, 새 비밀번호 같이 보내기를 넣었고 전부 거부됐다.
> 주소를 바꿀 수 있는 다른 API 는 설정 가져오기뿐이었고, 원래 비밀번호를 요구했다.

### 2.6 간헐 실패는 전후에서 수백 번 돌린다

간헐 실패가 이번 변경 때문인지 원래 있던 것인지는 **고치기 전과 후 커밋에서 같은 횟수로** 돌려서 가린다.

- **원인 없이 시간 상한만 늘리지 않는다.** 원인을 못 찾으면 못 찾았다고 보고하고, 다음 실패 때 가릴 수 있도록 실패 메시지에 진단 정보를 넣는다.

> 사례: jump 테스트가 전체 실행 중 한 번 실패했다. 고치기 전 커밋 300번 중 26번, 의심한 커밋 300번 중 19번 실패해서 원래 있던 것으로 판정했다.
> 원인은 서버가 연결 수를 늦게 올리는데 테스트가 한 번만 읽은 것이었고, 기다리며 읽도록 고친 뒤 300번 중 0번.

### 2.7 테스트는 실제로 열린 곳에 붙는다

테스트가 고른 포트·경로를 다른 프로세스가 먼저 잡으면, 가정한 주소로 붙는 테스트가 엉뚱한 곳에 붙는다.
**대상이 실제로 연 주소를 상태에서 읽어서** 붙는다.

> 사례: 테스트가 고른 포트의 127.0.0.1 쪽을 다른 프로세스가 먼저 잡자 터널은 [::1] 만 열었다.
> `127.0.0.1:port` 로 붙던 테스트 6개가 잘못 실패하고 1개는 잘못 통과했다.

### 2.8 안 쓰이는 코드는 빠진 호출인지 본다

"안 쓰는 함수" 경고는 지울 거리이기 전에, **불렀어야 하는데 빠진 곳**일 수 있다.
호출부를 전부 찾은 출력과 범위를 붙이고, 지울지는 따로 묻는다.

## 3. 고르기

후보는 `design-first` 2′ 표 형식으로 낸다 (`../../design-first/SKILL.md`). 여기서는 고르는 근거를 만드는 기법만 적는다.

### 3.1 "안 함" 도 근거를 붙여 추천한다

| 근거 | 사례 |
|------|------|
| 같은 권한으로 더 쉬운 길이 이미 있다 | 웹훅 테스트 응답으로 내부 포트를 탐색할 수 있다. 하지만 로그인한 운영자는 Host 주소만 바꿔도 같은 탐색을 할 수 있어서 안 함 |
| 고쳐도 병목이 다른 데 있다 | 전역 락 밖으로 DB 삭제를 옮겨도 DB 연결이 하나뿐이라 상태 조회는 여전히 기다린다. 나중 |
| 영향이 스스로 회복된다 | 상태 기록 경합으로 틀린 값이 들어가도 10초 안에 새 값으로 덮인다. 안 해도 됨 |
| 고치려면 새 절차가 필요하다 | 업데이트 서명은 릴리즈 절차와 서명 키 보관 장소가 먼저다. 키를 토큰과 같은 PC 에 두면 이득이 거의 없다 |

### 3.2 고치면 바뀌는 동작과 그 회귀를 같이 적는다

상한·검증을 새로 넣으면 **이미 저장된 값과 예전에 내보낸 파일**이 거부될 수 있다.

> 사례: 주기 설정에 상한 3600 을 넣으면 기존 설치가 시작할 때 거부된다. 그래서 시작할 때 3600 으로 보정하고 로그를 남겼다.
> 예전 버전에서 7200 을 저장한 채 내보낸 파일을 가져오면 400 이 나는 것도 이번 변경의 회귀라, 가져오기에도 같은 보정을 넣었다.

## 4. 고칠 때 넘길 것

고르고 나면 `design-first` → `plan-run` 으로 간다. 구현자에게 넘기는 작업 설명에 이 셋을 적는다.

- 재현이 먼저다. 재현되면 고치고, 안 되면 결과만 보고한다 (2절)
- 고치기 전 실패율과 고친 뒤 통과를 같은 조건으로 (2.1, 2.2)
- 보안 수정이면 돌아가는 길 시도 (2.5)
