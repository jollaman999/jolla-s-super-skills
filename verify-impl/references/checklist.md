# D 노드 상세 - 체크리스트 설계

## 항목 하나의 5필드

| 필드 | 규칙 | 나쁜 예 | 좋은 예 |
|------|------|---------|---------|
| `id` | `VF-NN` 고정 | - | `VF-03` |
| `대상` | 기능명 + `file:line` | "VM API" | `POST /api/v1/vm` (handler.go:142) |
| `방법` | live / static / frontend 중 하나 | - | live |
| `절차` | 복붙 가능한 명령 또는 조작 순서 | "호출해본다" | `curl -sS -X POST "$BASE/api/v1/vm" -H "Authorization: Bearer $TOKEN" -d @spec.json -w '\n%{http_code}'` |
| `판정기준` | 관측 가능한 pass/fail 조건 | "정상 동작" | pass: 201 + body에 `id` 존재 / fail: 그 외 |

**판정기준이 관측 불가능하면 항목이 아니다.** "잘 처리된다", "문제 없다"는 판정기준이 될 수 없다.

## 기능당 최소 세트

조회성 기능:
- 정상 조회 200 + 스키마
- 존재하지 않는 id → 404 (200에 빈 값이면 fail로 볼지 사용자에게 확인)
- 인증 없이 호출 → 401/403

상태 변경 기능:
- 정상 생성/수정 → 기대 상태코드 + 반환 식별자
- **생성 결과를 조회로 재확인** (쓰기만 보고 pass 하지 않는다)
- 잘못된 입력 → 400 + 에러 메시지 형태
- 인가 없는 주체 → 403
- (승인 시) 정리(cleanup) 절차

외부 연동 기능:
- 실제 외부 호출이 일어났는지 확인 수단 (로그/응답 필드/외부 상태 조회)
- 외부 실패 시 동작 - 목이 아닌 실제 경로로 확인 가능한지

## 항목 수 통제

- 심층 대상: 기능당 3~6 항목
- 그 외: 기능당 1~2 항목 (스모크)
- 전체가 40을 넘으면 E에서 사용자에게 **범위를 줄일지** 먼저 묻는다. 40개를 병렬로 돌리는 건 가능하지만 사용자가 리뷰하기 어렵다.

## E에서 사용자에게 물을 것

1. 빠진 항목 / 뺄 항목
2. 판정기준이 실제 요구사항과 다른 항목
3. 파괴적 호출(생성/삭제)을 포함해도 되는 항목과 환경
4. 정리(cleanup)까지 할지
