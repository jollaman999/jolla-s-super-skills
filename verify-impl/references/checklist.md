# D 노드 상세 - 체크리스트 설계

## 항목 하나가 갖춰야 할 것

| 필드 | 규칙 | 나쁜 예 | 좋은 예 |
|------|------|---------|---------|
| `id` | `VF-NN` 고정 | - | `VF-03` |
| `대상` | 기능명 + `file:line` | "VM API" | `POST /api/v1/vm` (handler.go:142) |
| `방법` | live / static / frontend 중 하나 | - | live |
| `절차` | 복붙 가능한 명령 또는 조작 순서 | "호출해본다" | `curl -sS -X POST "$BASE/api/v1/vm" -H "Authorization: Bearer $TOKEN" -d @spec.json -w '\n%{http_code}'` |
| `판정기준` | 관측 가능한 pass/fail 조건 | "정상 동작" | pass: 201 + body에 `id` 존재 / fail: 그 외 |

`기준출처` 와 `민감도` 는 D 노드에서 여기에 더 붙는다 (`SKILL.md`).

**판정기준이 관측 불가능하면 항목이 아니다.** "잘 처리된다", "문제 없다"는 판정기준이 될 수 없다.

**"에러 없음" 계열도 판정기준이 될 수 없다.** 무음 실패를 그대로 통과시킨다 -> `silent-failure.md`

| 쓰면 안 되는 것 | 대신 |
|-----------------|------|
| "에러 없이 응답" | "200 이고 items 길이 >= 1 이고 각 item 에 gpu_uuid 가 있음" |
| "200 이면 pass" | 본문 스키마와 최소 건수까지 명시 |
| "화면에 표시됨" | 표시된 값이 기대값과 같은지까지 |
| "로그에 에러 없음" | 기대 동작의 흔적(로그 라인·카운터·타임스탬프)이 있는지 |

값이 `0` / `N/A` / 빈 배열로 나오면 **진짜 그 값인지 수집 실패의 위장인지**를 다른 경로로 교차 확인한다.

## 기능당 최소 세트

조회성 기능:
- 정상 조회 200 + 스키마
- 존재하지 않는 id → 404 (200에 빈 값이면 fail로 볼지 사용자에게 확인)
- 인증 없이 호출 → 401/403

상태 변경 기능:
- 정상 생성/수정 → 기대 상태코드 + 반환 식별자
- **생성 결과를 조회로 재확인** (쓰기만 보고 pass 하지 않는다)
- 잘못된 입력 → 400 + 에러 메시지 형태
- 인가 없는 주체 → 403
- (승인 시) 정리(cleanup) 절차

외부 연동 기능:
- 실제 외부 호출이 일어났는지 확인 수단 (로그/응답 필드/외부 상태 조회)
- 외부 실패 시 동작 - 목이 아닌 실제 경로로 확인 가능한지

## 어느 검증에나 들어가는 4종 (정적)

접속 여부와 무관하게 **변경된 코드가 있으면** 아래를 항목으로 넣는다. 방법은 `static`.

| id 예 | 대상 | 판정기준 |
|-------|------|----------|
| VF-S1 | **민감 데이터** | 하드코딩된 비밀번호·토큰·개인키·개인정보가 **0건**. 있으면 `file:line` |
| VF-S2 | **중복 기능** | 새로 넣은 함수·모듈이 기존 것과 겹치지 않음. 겹치면 어느 것과 |
| VF-S3 | **미사용 코드** | 이번 변경으로 생긴 미사용 변수·함수·import 가 0건 |
| VF-S4 | **단계적 검증** | 추가/수정 단위를 먼저 확인하고, 그다음 전체 재확인 |

VF-S1 은 특히 놓치기 쉽다. repo 에 개인키가 커밋돼 있거나 설정 파일에 평문 비밀번호가 들어간 사례가 실제로 나온다.
**발견해도 고치지 않는다.** 보고만 한다.

## 언어별 게이트 (해당하면)

프로젝트가 정한 것이 있으면 그것을 따른다. 없으면 아래가 기본이다.

| 언어 | 항목 |
|------|------|
| Go | `gofmt`/`goimports` 차이 0건, `golangci-lint` 통과, 빌드 통과 |
| Go | `fmt.Println`/표준 `log` 미사용 (구조화 로깅으로 통일) |
| Go | 원시 `err.Error()` 를 API 응답으로 노출하지 않음 (구현 세부 유출) |
| Go | 요청/응답 구조체가 전용 model 패키지에 있고 `json`/`example`/`validate` 태그가 붙음 |
| Java/Spring | 빌드 통과, 컨트롤러 DTO 검증 애너테이션 |
| 공통 | 원시 예외 메시지를 응답 본문으로 그대로 내보내지 않음 |

## 항목 수 통제

- 심층 대상: 기능당 3~6 항목
- 그 외: 기능당 1~2 항목 (스모크)
- 전체가 40을 넘으면 E에서 사용자에게 **범위를 줄일지** 먼저 묻는다. 40개를 병렬로 실행하는 건 가능하지만 사용자가 리뷰하기 어렵다.

## E에서 사용자에게 물을 것

1. 빠진 항목 / 뺄 항목
2. 판정기준이 실제 요구사항과 다른 항목
3. 파괴적 호출(생성/삭제)을 포함해도 되는 항목과 환경
4. 정리(cleanup)까지 할지
