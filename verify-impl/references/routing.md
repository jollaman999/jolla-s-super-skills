# P 노드 - 경량/전체 경로 판정

## 왜 필요한가

세션 3,240건을 측정한 결과다. 지어낸 기준이 아니다.

| 관측 | 값 |
|------|-----|
| 프롬프트 길이 중앙값 | **40자** (Q1=22, Q3=71) |
| 60자 미만 짧은 요청 | **2,116건 = 65%** |
| 300자 초과 긴 요청 | 45건 = **1.4%** |

**평소 모드는 짧은 단발 요청이다.** 여기에 A~G 풀코스를 돌리면 과잉이다.
긴 요청(1.4%)만 성격이 다르다: 대상 명시 53%, 다중 요구 44%, 범위 전체 22%.

## 판정표

ODIN 식 실수 점수 대신 **관측 가능한 신호**로 판정한다. 틀렸을 때 어느 신호가 문제였는지 보이기 때문이다.

### 전체 경로 신호 - 하나라도 걸리면 full

| 신호 | 판별 |
|------|------|
| 다중 요구 | "그리고", "그다음", "또" 로 요구가 이어짐 |
| 범위 전체 | "전부", "전반적", "모두", "각각", "싹" |
| 대상 미특정 | "이 프로젝트", "소스 전반", 대상이 지목 안 됨 |
| 호스트 2개 이상 | 사이트 간 비교가 목적 |
| 배포 동반 | "릴리즈 찍고", "배포하고 나서", "반영하고" |
| 요청 200자 초과 | 상위 5%. 복합 요구일 가능성 높음 |
| 사용자가 명시 | "전체 검증", "다 확인해줘" |

### 경량 경로 신호 - 전체 신호가 하나도 없고 아래에 해당하면 light

| 신호 | 판별 |
|------|------|
| 60자 미만 | 중앙값 40자. 이게 평소 모드다 |
| 대상 하나 특정 | 엔드포인트 1개, 파일 1개, 호스트 1개, 기능 1개 |
| 단일 확인형 | "맞아?", "진짜야?", "되는거지?", "확인해봐" |
| 이미 명령이 주어짐 | 사용자가 `ssh ...` 나 `curl ...` 을 그대로 적어줌 |

### 애매하면

**한 줄로 묻는다.** 물어보는 비용이 잘못된 경로를 도는 비용보다 싸다.

> "이거 하나만 빠르게 확인할까요, 아니면 관련 기능 전체를 검증할까요?"

## 경로별 절차

### light - 경량

```
A·B (★1 동시)  ->  대상 1~3개 즉석 검증  ->  결과 보고
```

- **체크리스트 승인(E)을 생략한다.** 대신 **실행 직전에 무엇을 할지 한 줄로 알린다.**
- **실접속 승인(B′)은 생략하지 않는다.** 실제 노드에 붙는 건 항상 묻는다.
- **상태를 바꾸는 검증은 light 에서 하지 않는다.** 쓰기·재기동이 필요하면 그 시점에 full 로 승격한다.
- fail 이 나오면 그 항목만 `verify-diagnoser` 를 붙인다.
- F′ 반증은 생략한다. 단 결과가 pass 인데 근거가 약하면 그 사실을 보고에 적는다.

### full - 전체

`SKILL.md` 의 P → A·B → X·C → B′ → D → E → F → F′ → H → R → G 를 그대로 돈다.

## 승격 규칙

light 로 시작했어도 아래가 나오면 **즉시 full 로 올리고 사용자에게 알린다.**

- 상태 변경이 필요해짐 (재기동, DB 쓰기, 배포)
- 호스트가 2개 이상으로 늘어남
- 확인할 항목이 5개를 넘어감
- fail 이 3건 이상 나옴 (단발 문제가 아니라는 뜻)

> "생각보다 범위가 넓어져서 체크리스트를 만들어 승인받고 진행하겠습니다."

## 강등하지 않는다

full 로 시작했으면 중간에 light 로 내리지 않는다. 사용자가 전체를 요청한 것이므로 범위를 임의로 줄이는 게 된다.
범위를 줄이려면 **사용자에게 물어본다.**
