# D·E 노드 - 민감도 판정

사용자가 위험한 항목을 찾아내게 하지 않는다. **내가 먼저 판정해서 E에서 짚어준다.**

## 민감도 등급

| 등급 | 뜻 | E에서의 처리 |
|------|-----|--------------|
| `안전` | 읽기만, 상태 안 바뀜 | 표에만 표시 |
| `주의` | 상태 바뀌지만 되돌리기 쉬움 | 표에 표시 + 되돌리는 법 한 줄 |
| `위험` | 되돌리기 어렵거나 남에게 영향 | **개별로 따로 묻는다** |

## 위험 판정 신호 - 하나라도 걸리면 `위험`

| 신호 | 예 |
|------|-----|
| 운영 환경 | prod, 사내 실노드, 다른 사람이 쓰는 서버 |
| 서비스 중단 | 재기동, `docker restart`, 컨테이너 down, 배포 |
| 데이터 변경 | DB write/update/delete, 인덱스·버킷 삭제 |
| 리소스 생성 | CSP 인스턴스·K8s 클러스터 생성 (비용 + 잔여물) |
| 되돌리기 어려움 | 삭제, force, 덮어쓰기, 백업 없는 변경 |
| 외부 영향 | 알림 발송, 웹훅, 외부 API 상태 변경 |
| **git 쓰기** | commit, push, **force push**, tag, branch 삭제 |
| 범위 밖 | 지시받은 대상 밖의 파일·호스트·브랜치 |

## 순서 의존성

**순서를 틀리면 되돌릴 수 없는 조합이 있다.** 항목 각각은 안전해도 순서가 틀리면 사고가 난다.

> "재설치를 먼저하고 데이터날리고 가동했어야지"

D 에서 아래를 확인하고, 걸리면 **실행 순서를 명시**한 뒤 E 에서 함께 승인받는다.

| 조합 | 올바른 순서 | 틀리면 |
|------|-------------|--------|
| 재설치 + 데이터 초기화 | 재설치 → 데이터 초기화 → 기동 | 새 스키마에 옛 데이터가 남음 |
| 배포 + 검증 | 배포 → **반영 확인** → 검증 | 옛 바이너리를 검증하고 pass 판정 |
| 설정 변경 + 재기동 | 백업 → 변경 → 재기동 → 확인 | 원복 불가 |
| 생성 + 정리 | 생성 → 검증 → 정리 | 검증 전에 지워버림 |
| 마이그레이션 + 원본 정리 | 마이그레이션 → **검증** → 원본 정리 | 실패했는데 원본이 없음 |

순서가 중요한 항목은 체크리스트에 `순서: VF-03 → VF-05 → VF-07` 로 적고,
**병렬군(★)에 넣지 않는다.** 순서 의존 항목을 동시에 실행하면 순서가 깨진다.

## 주의 판정 신호

- 로컬 구동 (포트 점유, 이미지 다운로드)
- 임시 파일 원격 생성 (`/tmp/*.sh`)
- 캐시·세션 무효화
- 읽기지만 무거운 것 (전체 로그 수집, 대량 쿼리)

## E에서 제시하는 형태

```
아래는 신경 쓰셔야 할 항목입니다:

[위험] VF-05 - 10.0.0.11(운영)에서 app-svc 재기동
        영향: 재기동 중 수집 중단 약 20초
        되돌리기: 자동 복구, 실패 시 run_app-svc.sh 재실행
        → 진행할까요?

[위험] VF-07 - agent DB에 INSERT (테스트 호스트 1건)
        되돌리기: 검증 후 DELETE 하겠습니다 / 남길까요?

[주의] VF-03 - 로컬 8080 포트 점유 (현재 사용 중인 프로세스 없음)
```

## 판정할 수 없을 때

되돌릴 수 있는지 확신이 안 서면 **`위험`으로 올린다.** 낮춰 잡는 쪽이 훨씬 비싸다.
