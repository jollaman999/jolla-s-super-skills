# 프론트엔드 겸용 프로젝트 검증

B에서 프론트 존재가 확인되면 B′에서 아래를 **함께** 묻는다 (나중에 따로 묻지 않는다):

- 프론트 URL (dev/stg 중 어디)
- 로그인 방식: 폼 로그인 / OAuth / SSO / 토큰 직접 주입
- 테스트 계정 - **아이디는 받되 비밀번호는 env 변수명으로** (`$TEST_PW`)
- 프론트+백엔드 연계 검증까지 할지, 아니면 API만 할지
- 브라우저 자동화 가능 여부 (playwright/puppeteer가 repo에 있는지, 없으면 설치해도 되는지)

## 연계 검증의 요점

프론트를 따로, 백엔드를 따로 검증하면 **둘 사이 계약 불일치**를 놓친다. 연계 검증은 그 경계를 본다:

| 확인 대상 | 방법 |
|-----------|------|
| 로그인 → 토큰 발급 → 이후 요청에 실림 | 로그인 후 네트워크 요청 헤더 확인 |
| 프론트가 부르는 경로가 백엔드에 실재 | 프론트 API 호출부 grep → 백엔드 라우터와 대조 (`static`으로도 가능) |
| 응답 필드명이 프론트 기대와 일치 | **백엔드 응답 클래스의 필드 선언** vs 프론트 파싱 코드. 목(mock)과 대조하지 않는다. |
| 목과 백엔드가 어긋나 있지 않은가 | 어긋나면 그 자체가 발견 항목 |
| deprecated 경로를 쓰고 있지 않은가 | 백엔드의 `@Deprecated` 핸들러를 프론트가 부르는지 |
| 프론트가 보내는 파라미터를 백엔드가 받는가 | 안 받는 파라미터는 조용히 버려진다. |
| 에러 응답이 화면에 표시됨 | 의도적 실패 요청 → 화면 상태 |
| 권한 없는 화면 접근 차단 | 저권한 계정으로 직접 URL 진입 |

## 목(mock)이 버그를 가린다

**프론트의 목이 백엔드가 아니라 프론트 기대에 맞춰져 있으면, 목은 계약 검증 역할을 못 하고 오히려 버그를 감춘다.**

실제로 잡힌 사례:

```
프론트  constants.ts:209   anomaly?.eccDoubleBitErrors      <- 이 이름으로 읽는다
타입    type.ts:437        eccDoubleBitErrors?: number
목      mocks/....ts:761   eccDoubleBitErrors: xidCount     <- 목도 같은 이름으로 준다
백엔드  NodeGpuSummaryResponse.java:72   private Double xidErrors   <- 실제로는 이 이름
```

목 모드에서는 값이 정상으로 보이고, 실서버에서만 `undefined` 가 되어 화면에 `-` 만 뜬다.
예외도 안 나고 콘솔 에러도 없다. **전형적인 무음 실패다** (`silent-failure.md`).

- **목은 검증 근거가 아니다.** 목이 통과했다는 것은 아무것도 증명하지 않는다.
- 응답 필드명은 **백엔드 응답 클래스와 직접 대조**한다. 목과 대조하면 같은 오탈자가 양쪽에 있어 통과한다.
- 목과 백엔드가 어긋나 있으면 **그 자체가 발견 항목**이다. 목이 낡은 계약을 붙잡고 있다는 뜻이다.

### 대조 방법 (접속 없이 가능)

```sh
grep -rn '<필드명>' <front>/src --include='*.ts' --include='*.tsx' | grep -v '/mocks/'
sed -n '/class <ResponseClass>/,/^    }/p' <back>/.../<X>Response.java | grep private
```

**백엔드에 같은 이름의 *메서드* 가 있다고 필드가 있는 것이 아니다.**
위 사례에서 백엔드에 `eccDoubleBitErrors` 가 9건 있었으나 전부 시계열 쿼리 메서드명이었고,
직렬화되는 응답 필드는 `xidErrors` 뿐이었다. **응답 클래스의 필드 선언만 본다.**

## 범위를 먼저 좁힌다

프론트의 baseURL 이 여러 종이면 **이 repo 소관 prefix 만** 대조한다.
게이트웨이 뒤 다른 서비스로 가는 경로를 같이 대조하면 "백엔드에 없음" 이 전부 오탐이 된다.
제외한 prefix 는 "대조 대상 아님" 으로 한 줄 남긴다.

## 실행 방법 (가능한 것부터)

1. **API 레벨 재현** (권장 기본값) - 브라우저 없이 로그인 API → 토큰 → 프론트가 부르는 것과 같은 순서로 호출. 빠르고 안정적이며 계약 불일치 대부분을 잡는다.
2. **브라우저 자동화** - 렌더링/라우팅 가드/에러 표시처럼 API로 재현 안 되는 항목만. playwright가 이미 있으면 사용, 없으면 사용자에게 설치 여부를 묻는다.
3. **정적 대조** - 프론트 호출부와 백엔드 라우터를 `file:line`으로 대조. 접속 불가일 때의 폴백.

## 주의

- 스크린샷/HAR에 토큰이 찍힐 수 있다. 증거로 첨부하기 전에 마스킹한다.
- 프론트 항목은 `방법: frontend`로 표시해 F에서 병렬군에 함께 들어간다.
- prod 프론트에 로그인해 상태를 바꾸는 조작은 E에서 명시 승인된 것만.
