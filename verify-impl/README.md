# verify-impl

소스에 구현된 기능을 파악하고, **실제 노드에 붙거나 로컬에 띄워서** 정말 도는지 확인합니다.

> "검증해줘", "제대로 동작하는지 확인", "왜 안되는지 확인", "접속해서 확인"

코드 리뷰가 아닙니다. 버그를 찾는 것이 아니라 **된다고 들은 것이 실제로 되는지**를 봅니다.

"된다고 들은 것" 은 사용자가 말한 기대 상태, 붙여넣은 curl·에러 로그, 또는 openapi 같은 문서입니다.
그런 근거가 하나도 없으면 코드를 읽어 기준을 세우되, **그건 제가 정한 기준이므로 승인 단계에서 따로 짚어 묻습니다.**
커밋 메시지는 근거로 쓰지 않습니다.
버그 헌팅은 `/code-review` 쪽입니다.

## 전제

**"에러가 없다" 는 통과가 아닙니다.**
이 계열 코드베이스에서 가장 흔한 실패는 예외가 아니라 조용히 틀린 값을 내는 무음 실패입니다.
그래서 기대한 동작의 흔적이 관측돼야 통과로 칩니다. 소스의 주석이나 함수 이름도 근거로 쓰지 않습니다.

그리고 **손으로 돌린 결과는 운영에서 도는 결과가 아닙니다.** 권한과 환경이 다릅니다.

## 팀으로 움직입니다

팀장(`SKILL.md`)은 경로 판정, 사람과의 대화, 판단, 종합만 합니다.
탐색·실행·반증·진단은 서브에이전트 8명이 병렬로 합니다.

컨텍스트가 격리돼 있어서 **로그 수천 줄이 팀원 쪽에서 끝나고 팀장에게는 정리된 JSON 만** 올라옵니다.

| 팀원 | 담당 | 몇 명이 동시에 |
|------|------|----------------|
| `verify-inventory` | 기능 인벤토리 | 1 |
| `verify-target-scout` | 접속 대상·프론트 탐색 | 1 |
| `verify-crosscheck` | 구현과 API 스펙 대조 | 1 |
| `verify-host` | 호스트 한 대 전담 검증 | 호스트 수만큼 |
| `verify-frontend` | 프론트와 백엔드 연계 | 1 |
| `verify-refuter` | 통과 판정 반증 | 통과 항목 수만큼 |
| `verify-diagnoser` | 실패 원인 추적 | 실패 항목 수만큼 |
| `verify-differ` | 호스트 간 결과 차이 원인 | 갈린 항목 수만큼 |

팀원 정의는 [`../agents/`](../agents/) 에 있습니다.

## 흐름

```
동시 세션 확인 -> 이전 진행 확인 -> 경로 판정
  -> 기능 인벤토리 · 접속 대상 탐색      (병렬)
  -> 계획 제시하고 시작 신호 대기        (블로킹)
  -> 실접속 승인                          (블로킹)
  -> 체크리스트 + 민감도 + 기준출처 제시하고 승인   (블로킹)
  -> 호스트별 병렬 실증
  -> 통과 항목 반증
  -> 실패 항목 원인 추적
  -> 종합 보고
```

블로킹 지점이 세 군데 있습니다. **승인 없이는 다음으로 넘어가지 않습니다.**

### 무엇을 정상으로 볼지는 사람이 정합니다

체크리스트의 각 항목에는 판정기준과 함께 **그 기준을 어디서 가져왔는지**가 붙습니다.

| 기준출처 | 뜻 |
|---------|-----|
| `사용자` | 사용자가 말한 것을 그대로 옮겼습니다 |
| `curl` · `로그` | 붙여넣은 요청·에러에서 뽑았습니다 |
| `문서` | openapi 등에 적힌 대로입니다 |
| `코드` | **아무도 말해준 적 없어서 제가 코드를 읽고 정했습니다** |

승인 단계에서 **`코드` 출처만 따로 뽑아 "이 기준이 맞습니까" 를 묻습니다.**
민감 항목은 "해도 되나" 를 묻는 것이고, 이건 "제가 정한 정상의 정의가 맞나" 를 묻는 것이라 성격이 다릅니다.

의도된 동작을 버그로 오인하는 일이 여기서 걸립니다. 예를 들어 passthrough 구성에서는
GPU 텔레메트리가 0건인 게 정상인데, 코드만 봐서는 알 수 없습니다. 그래서 묻습니다.

`코드` 출처가 하나도 없으면 이 질문은 건너뜁니다. 전부 사용자가 준 기준이면 물을 게 없습니다.

### 짧은 요청에 풀코스를 돌리지 않습니다

세션 3,240건을 재어 보니 프롬프트 중앙값이 40자였고 65%가 60자 미만이었습니다.
"이거 되나 확인해줘" 한 줄에 8명을 띄우는 것이 이 skill 의 가장 흔한 실패라
경로 판정 노드가 `light` 와 `full` 을 먼저 가릅니다.

`light` 는 탐색 후 1~3건만 즉석 확인하고 끝냅니다. 다만 **실접속 승인은 어느 경로에서도 생략하지 않습니다.**

### 통과에도 반증을 붙입니다

통과가 나오면 `verify-refuter` 가 항목마다 따로 붙어 그 판정을 깨려고 시도합니다.
반증에 실패해야 최종 통과이고, 반증에 성공하면 `disputed` 로 따로 표기합니다.

확증 편향을 막으려고 팀장과 컨텍스트를 분리했습니다. 판정한 쪽이 스스로 검토하면 잘 안 깨집니다.

### 실패는 원인까지 갑니다

"실패했습니다" 로 끝내지 않습니다. 실제 요청은 거의 항상 "왜 안되는지" 까지이기 때문입니다.
다만 **진단만 하고 고치지는 않습니다.** 원인과 수정안을 올리고, 고칠지는 사람이 정합니다.

수정 후 "다시 확인해줘" 가 오면 실패했던 항목만 재검증합니다.
그때 **배포 반영을 먼저 확인합니다.** 수정이 원격에 안 올라간 채로 재검증하면 같은 실패가 또 나옵니다.

## 안전장치

- 실제 노드에 붙는 것 자체가 승인 대상입니다. 거부되면 로컬 구동으로 갑니다
- 체크리스트를 낼 때 **위험 항목을 미리 짚어서** 같이 묻습니다. 사용자가 하나씩 찾아내게 하지 않습니다
- **제가 지어낸 판정기준은 따로 표시해서 승인받습니다.** 무엇이 정상인지는 코드가 아니라 사람이 압니다
- 발견한 문제를 고치지 않습니다. 원인과 수정안까지만 올리고 고칠지는 사용자가 정합니다
- 검증하러 들어간 노드에서 소스를 직접 고치지 않습니다. 그러면 그 노드는 더 이상 검증 환경이 아닙니다
- 비밀번호와 토큰은 세션 안에서만 기억하고 파일에 쓰지 않습니다. 출력에서는 마스킹합니다
- 긴 검증은 진행 상태를 남깁니다. 중간에 끊겨도 처음부터 다시 하지 않습니다

## 구성

| 경로 | 내용 |
|------|------|
| `SKILL.md` | 실행 그래프와 노드별 규칙 |
| `references/` | 판정 기준, SSH 레시피, 경계 조건, 무음 실패 패턴, 내가 틀렸던 방식 |
| `templates/` | 체크리스트·보고서·접속 대상 양식 |
| `scripts/` | 아래 참조 |
| `evals/cases.md` | 평가 케이스와 스크립트 회귀 |

### scripts

모델의 "된 것 같다" 를 exit code 로 차단하는 것이 목적입니다.

| 스크립트 | 하는 일 |
|----------|---------|
| `verify-run.sh <id> <기대코드> <curl 인자...>` | 한 항목을 실행하고 결정적으로 판정, JSON 반환 |
| `ssh-run.sh` | 원격 실행. timeout, 점프호스트, 시크릿 마스킹, 접속 실패 시 경로 진단 내장 |
| `health-wait.sh <url\|docker:이름> [상한] [간격]` | 헬스 통과까지 상한을 두고 폴링. 무한 대기 없음 |
| `probe.sh <base_url> [path]` | 도달성 확인. 실패하면 그 항목은 `unknown` |
| `scan-targets.sh [repo]` | 접속 대상 후보 스캔. **값은 안 찍고 변수명과 위치만** |
