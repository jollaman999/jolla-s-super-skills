# 제출 양식

심사·관리 부서에 내는 문서다. **양식이 구성을 정한다.** 아래 틀은 양식에서 빠진 것을 메우는 규칙이지
양식을 바꾸는 근거가 아니다.

| 종류 | 본보기 원문 | 이 파일에 있는 것 |
|------|-------------|-------------------|
| 정부과제 보고서 (실적보고서, 시험계획서) | 없음 | 규칙 |
| 사업계획서 | 없음 | 규칙 |
| 요구사항 정의서 | 없음 | 규칙 |
| 제안서 | 없음 | 규칙과 검사 |
| SW 등록 명세서 | 있음 (사용자가 받아들인 최종본) | 틀과 규칙 |

본보기 원문이 없는 종류는 사용자가 준 양식과 예시가 틀이다. 여기 없는 구성을 지어내지 않는다.

## 1. 공통

| 규칙 | 근거 |
|------|------|
| 쓰기 전에 "양식 어느 절·표·칸에 무엇을" 체크리스트를 만든다 | `writing.md` 1절 |
| 우리 담당 칸만 쓴다. 남의 칸은 고치지 않는다. 공동 칸은 우리 몫만 | `questions.md` 1.1 |
| 남이 주관하는 목표·지표는 채우지 않는다 | "정량적 목표는 <기관> 주관이라서" |
| 미정은 "협의 필요", 근거 없는 칸은 "추정"·"원본 확인 필요" | `writing.md` 2절 |
| 사용자가 준 KPI 후보, 표 양식, 배정은 바꾸지 않는다 | `writing.md` 2절 |
| 수치는 확실한 하한으로 ("4+종") | `writing.md` 2절 |
| 해를 가리키는 문서는 그해 자료만 근거로 | `questions.md` 1.6 |
| 남이 만든 양식을 고치면 변경 추적으로 남기고 메모는 그대로 둔다 | `hwp.md` 5절 |
| 끝말·깊이·괄호·ID 체계는 같은 양식의 예시를 따른다 | "예시가 있는데 스타일을 왜 다 무시하고" |

## 2. 정부과제 보고서

hwp/hwpx 양식의 칸을 채운다. 작업 순서는 `hwp.md` 3절.

**목표는 세 단계로 쓴다.**

| 단계 | 무엇 | 쓰는 법 |
|------|------|---------|
| 1depth | 목표 | 한 줄 |
| 2depth | 세부목표 | 목표 아래. 개수를 맞춘다 (예: 목표마다 4개) |
| 3depth | 할 일 | 끝말을 "설계", "개발", "구현" 으로. 괄호를 쓰지 않는다 |

근거: 이 PC 세션 교정 (원문 미보존). 개수와 끝말은 그 양식에서 사용자가 정한 값이다.
다른 양식에 예시가 있으면 예시를 따른다.

## 3. 사업계획서

| 규칙 | 근거 |
|------|------|
| 기관마다 맡은 일은 최신 분담 근거로 쓴다. 계획서 원문과 회의 결정이 다르면 둘을 나눠 적는다 | `questions.md` 1.3 |
| 우리 쪽으로 일을 더 몰지 않는다 | "왜 자꾸 니는 우리쪽으로 몰을려그래" |
| 우리가 고려할 요소가 아닌 것은 넣지 않는다 | "이것들은 우리가 고려할 요소가 아니야" |

## 4. 요구사항 정의서

| 규칙 | 근거 |
|------|------|
| 요구사항은 추상적으로 쓴다. 무엇이 되어야 하는지이지 어떻게 만드는지가 아니다 | 이 PC 세션 교정 (원문 미보존) |
| ID 체계(`REQ-001` 같은 번호 모양)와 칸 구성은 양식의 기존 행을 따른다 | 같은 세션 |
| docx 는 `why-hwp text` 로 읽는다. 고칠 도구가 없으면 md 로 쓰고 "어느 행·칸에 무엇을" 표를 같이 낸다 (판단) | 설계 결정: why-hwp 범위는 docx 텍스트 추출까지 |

## 5. 제안서

| 규칙 | 근거 |
|------|------|
| 특정 제품·도구·업체 이름 대신 기능 이름으로 쓴다 | 이 PC 세션 교정 (원문 미보존) |
| 끝에 금지어 검사를 한다. 금지어 목록은 사용자에게 받거나, 자료의 제품·업체 이름으로 만들어 보인다 | 같은 세션 |
| 그림 원본(SVG)도 같은 목록으로 grep 한다. PNG·캡처 속 글자는 눈으로 | 빼라고 한 이름이 그림 SVG 에 남아 있던 일 |

## 6. SW 등록 명세서

사용자가 준 다른 프로그램의 명세서(PDF)를 보고 칸마다 쓰는 방식을 먼저 짚은 뒤 썼다.
칸 이름은 양식에 따라 다르다. 아래는 "제목 / 특징 / 주요기능 / 사용방법" 양식의 틀이다.

```markdown
# <프로그램 이름>

## 본 프로그램의 특징

<무엇>을 <어떻게> 하는 <구성 요소 1>과, <무엇>을 하는 <구성 요소 2>를 각각 독립 프로세스로 구성한 프로그램으로, <핵심 방식>으로 <무엇>을 통제하고 <부가 기능>을 하는 <분야> 프레임워크

## 주요기능

o <대항목 1> (<구성 요소 1>)
 - <대상> 등록·조회·삭제 및 버전 교체
 - <입력>과 <기준>을 대조하는 <방식> 기반 <기능> (<한계·성질>)
 - <동작> 및 <결과> 확인
o <대항목 2> (<구성 요소 2>)
 - <흐름 이름>(<단계> → <단계> → <단계>) 실행
 - 단계별 상태(<상태 목록>) 기록
o <이력·API·화면 같은 공통 기능>

## 사용방법

- <필요한 것> 설치
- 설정 파일 작성 (<무엇> 등록)
- 앱 실행 (<어떻게 기동>)
- <쓰는 순서 한 줄>
- <입력>을 전달하면 <결과>를 수행함
```

| 칸 | 쓰는 법 |
|----|---------|
| 특징 | 마침표 없는 한 문장 한 문단. "~하는 프로그램으로, ~하는 프레임워크" 로 끝난다 |
| 주요기능 | `o` 대항목 + ` - ` 세부. 명사형으로 끝난다 |
| 사용방법 | `-` 단계. 명사형이나 "~함" 으로 끝난다 |

| 규칙 | 근거 |
|------|------|
| **이름은 이번에 실제로 한 일로 좁힌다.** 다음 해 등록 이름에 몫을 남긴다. 후보 셋과 각 범위를 보이고 고르게 한다 | "앞으로 4년동안 또 소프트웨어 등록할때 이름이 지장 가니까 다른 이름으로 해줘" |
| **우리 몫이 아닌 것처럼 읽히는 줄은 고친다.** 협업 기관 몫(예: 자연어 해석)으로 읽히는 줄은 우리가 실제로 한 방식으로 바꾸고 코드 위치로 근거를 댄다 | "우리몫이라오확실하게 구분해줘" |
| 같은 문구가 README·설계 문서에 있으면 같이 고친다 | "README 도 그렇게 고쳐줘" |
| 고친 뒤 응답 첫머리에 바꾼 줄과 그대로 둔 것을 적는다 | 전역 규칙 ("화면을 조금씩 고치는 요청") |
