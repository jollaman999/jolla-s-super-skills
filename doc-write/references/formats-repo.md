# repo 문서

repo 안에 두는 문서다. 독자가 누구냐에 따라 갈린다.

| 종류 | 독자 | 그림 |
|------|------|------|
| 외부 README | 처음 보는 개발자, 다른 기관 | 직접 그린 SVG |
| 공개 설계 문서 | 외부 검토자 | 직접 그린 SVG (스타일 B) |
| 협업 기관 공유 문서 | 다른 기관 개발자 | 직접 그린 SVG, 데이터 모델 그림 |
| 개발자 repo 문서 | 그 repo 개발자 | 그 repo 규약 |
| 시험 기록 | 공유 문서를 읽고 따라 해 볼 사람 | 실제 화면 캡처 |

## 1. 외부 README

**사용자가 든 항목이 곧 목차다.** 기록처럼 쓰지 않는다 ("우리가 뭘 했는지 기록 같아 보이자나").

절 순서 (사용자가 받아들인 것)

| # | 절 | 무엇 |
|---|-----|------|
| 1 | What it does | 하는 일과 **하지 않는 일** |
| 2 | Architecture | 그림 + 프로세스 표 |
| 3 | Quick start | 설정 없이 로컬 실행 → 컨테이너 → 실제 환경 |
| 4 | Using it with <연동 대상> | 무엇을 부르는지, 요건 |
| 5 | How partners use it | 기관별 활용과 가이드 링크 |
| 6 | API | 경로 요약 표 |
| 7 | Documentation map | 문서 지도. docs 가 어느 언어인지도 |
| 8 | What works today | 되는 것 |
| 9 | Limitations | 안 되는 것 |
| 10 | Roadmap | 남은 것 |
| 11 | Configuration | 핵심 변수 표, 전체는 `<details>` 로 접음 |
| 12 | Development | 빌드·시험 |
| 13 | License | |

| 규칙 | 근거 |
|------|------|
| 언어판 전환 링크는 맨 위 왼쪽 한 줄. 영어판 `<p align="left"><b>English</b> \| <a href="README.ko.md">한국어</a></p>` | "언어 전환 링크가 우측 위에 말고 좌측 위로 해달라니까" |
| 언어판은 같은 구성으로 같이 고친다. reference 문서도 | "reference 문서에도 macOS xattr 안내 넣고" |
| 빠른 시작은 직접 돌려 본다. 못 돌린 것은 못 돌렸다고 쓴다 | `writing.md` 8절 |
| 한글판 그림은 ASCII 대신 SVG | 한글 폭 때문에 ASCII 상자 줄이 안 맞음 |
| API 경로 목록은 라우터 코드와 대조하고, 링크 깨짐 0건을 확인한다 | 사용자가 받아들인 README |
| 개편 이력과 옛 기록은 빼고 "git 기록에 있다" 고 보고한다 | `writing.md` 2절 최종본 |
| OS 마다 다른 명령(실행 권한, 격리 속성 해제, 초기 비밀번호 위치)은 OS 별로 나눠 쓴다 | 4개 언어 README 세션 |

## 2. 공개 설계 문서

사용자가 다른 문서의 본보기로 지목한 설계 문서의 틀이다 ("docs 그림이나 내용들을 <본보기 문서> 처럼 해줘봐").

```markdown
# <무엇> 설계 (<핵심 방식>)

---

## 한 장 요약

![목표 구조](figures/04-target.svg)

| 질문 | 답 |
|---|---|
| 무엇을 만드나 | <한 문장> |
| <핵심 질문 1> | **<결론>.** <이유> (3.1) |
| <핵심 질문 2> | **<결론>.** <이유> (3.3, 3.10) |

---

## 1. 목표와 요구사항

| # | 요구 | 이 설계에서 |
|---|---|---|
| R1 | <사용자가 말한 요구> | <어떻게 했나 한 줄> |

**처음 나오는 말**
- **<용어>**(<풀어 쓴 원어>): <한 줄 풀이>

---

## 3. 설계 결정 - 후보와 고른 이유

결정마다 **어떤 방법들이 있는지**, **무엇을 골랐는지**, **왜 골랐는지**, **무엇을 포기했는지**를 적는다.

### 3.1 <결정할 것>

![<비교 그림>](figures/03-options.svg)

| 방법 | 어떻게 동작하나 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **① <방법>** (선택) | <동작> | <얻는 것> | <잃는 것> |
| ② <방법> | <동작> | <얻는 것> | <잃는 것> |
```

| 틀 | 무엇 |
|-----|------|
| 한 장 요약 | 제목 바로 아래. 큰 그림 + 질문/답 표. 답 끝에 상세 절 번호를 괄호로 |
| 요구사항 표 | 사용자가 말한 요구를 R 번호로, "이 설계에서" 어떻게 했는지 한 줄 |
| 처음 나오는 말 | 굵은 용어 + 한 줄 풀이. 약어는 풀어 쓴 원어를 괄호로 |
| 결정 절 | 비교 그림 + 방법 / 어떻게 동작하나 / 얻는 것 / 잃는 것 표, 고른 행에 "(선택)" |
| 절 제목 | 결론을 제목에 넣는다 ("<무엇> - <A> 대신 <B>"). 사용자가 대화에서 물은 것은 그 질문이 절 제목이 된다 ("평소 복제는 누가 하나") |
| 뒤쪽 | PoC 결과, 도입 순서, 위험과 확인이 필요한 것, 부록(설정 초안, 참고 문서) |

**공개로 쓰는 법.** 지금 운영 구조, 사내 소스 경로, 사내 제품 이름, 옮겨 가는 순서를 빼고 처음부터 짓는 기술 설계로 쓴다.
사내 이름은 "관리 서버" 같은 일반 이름으로 바꾼다. 남겨도 되는 이름은 사용자가 정한다
("소스적인 부분 다 빼고 ... 그러면 완전히 공개해도 문제 될꺼 없으니까").

## 3. 협업 기관 공유 문서

다른 기관이 우리 API 를 보고 연동하는 문서다. **코드가 아니라 동작을 쓴다**
("코드를 설명하는건 아니고 동작을 설명해야해 다른기관은 우리 api들을 참고할꺼고").

| 절 | 무엇 |
|-----|------|
| 한 장 요약 | 질문/답 표. "무엇을 하나", "기관마다 무엇을 하나", "어떻게 진행되나", "언제 성공인가", "실제로 돌려 봤나" |
| 하는 일 | 처음 나오는 말을 "말 / 뜻" 표로 |
| 전체 흐름 | 그림 |
| 쓰는 외부 도구 | 무엇인지와 어떻게 동작하는지 |
| 부르는 순서, 인증, 오류와 상태 코드 | 표 |
| 비동기 동작 | 진행을 보는 법 |
| API 목록 | 묶음마다. 목록이 페이지로 나뉘면 그것부터 |
| 요청 모양, 알아 둘 것 | 예시 JSON |
| 예시와 실제 화면 | 시험한 환경과 화면 캡처 |

| 규칙 | 근거 |
|------|------|
| 공통 가이드와 기관별 문서를 나눈다. 기관별 문서는 그 기관이 할 일만 | 사용자가 받아들인 구성 |
| 기관 몫과 우리 몫을 표로 가른다. 기관 몫은 "자리만 있다" 처럼 지금 상태로 쓴다 | `writing.md` 2절 |
| 상대 기관의 내부 자료를 공개 문서에 인용해도 되는지 묻는다. 발표자 이름은 넣지 않는다 | 협업 기관 연동 문서 세션 |
| 데이터 모델은 `figures.md` 5절 그림 + 실제 데이터 한 건 | "필드들믈 세로로 쭉 나열하고 ..." |

## 4. 개발자 repo 문서

**그 repo 의 문서 규약을 따른다.** 규약이 없으면 아래를 쓴다 (사용자 repo 의 문서 규약에서 가져온 것).

| 무엇 | 어떻게 |
|------|--------|
| 어디에 두나 | 시스템 개요·개발환경·빠른 시작은 루트 `README.md`, 상세 설계·흐름은 `docs/*.md` |
| 골격 | 제목 → 맨 위 blockquote 로 무엇인지·읽는 순서·경고 → 목적 한 줄 → 표 중심 본문 → 남은 것 |
| 형식 | 표 우선. 근거는 `파일:라인`. 문단은 3~4줄에서 끊는다. 기술 용어는 원어, 단정형 |
| 그림 | 규약이 Mermaid 면 `.mmd` 와 렌더본을 같은 이름으로 (`figures.md` 8절) |
| 근거 확인 | `file:line` 이 실제 줄과 맞는지 직접 연다 |

## 5. 시험 기록

| 넣을 것 | 근거 |
|---------|------|
| 환경 버전, 노드 사양·이미지·드라이버 | "테스트한 내용도 문서에 포함해" |
| 배포마다 걸린 시간과 바깥에서 본 결과 | 같은 발화 |
| 막힌 것 (증상·원인·처리) | 같은 발화 |
| 시험 중 넣은 커밋, 남은 것 | 같은 발화 |
| 시험하지 못한 것과 이유 | 사용자가 받아들인 형태 |

목록을 계단식으로 달라고 하면 `-` 들여쓰기로 쓴다.

```markdown
## 실제 환경

- <OS 이름 버전>
  - <클라우드> <인스턴스 종류> (<이미지>)
    - <구성 요소>: <어떻게 들어갔나>
    - 배포: <무엇>
- <OS 이름 버전>
  - ...

## 시험하지 못한 것

- <OS 이름>
  - <클라우드>: <이유>
```
