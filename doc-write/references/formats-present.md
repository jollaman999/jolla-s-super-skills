# 발표·리뷰

코드를 모르는 회의 참석자가 보는 문서다. 목적과 동작을 쓰고 코드 위치를 뺀다
("코드 적으로 말고 이거 발표 자료로 쓸거야 남들이 볼때 이해할수 있게").

## 1. 발표 pptx (워크샵 등)

| 규칙 | 근거 |
|------|------|
| **지정 템플릿 덱을 복사해서 고친다.** 처음부터 새 덱을 만들지 않는다 | 생성 라이브러리로 처음부터 만든 덱이 거절됨 |
| **로고는 슬라이드가 아니라 레이아웃(`slideLayout`) 안 그룹에 있다.** 복사한 덱의 로고가 우리 것인지 본다 | "로고가 <다른 과제> 꺼로 바꼈는데?" |
| **모듈마다 슬라이드를 나눈다** | "한곳에 다담으면 ... 이걸 어떻게 보여줘" |
| **API·Swagger 화면 말고 실제 결과 화면을 넣는다** | 이 PC 세션 교정 (원문 미보존) |
| **최종본 그림은 네이티브 도형으로 그린다.** 현재 vs 개선 비교, ①②③ 흐름 | 같은 세션 |
| **끝말은 명사형** ("~개선", "~지원") | 같은 세션 |
| **QA 는 레이아웃만 보지 않는다.** 로고, 다른 과제 이름, 맞는 해의 자료, 우리 몫인지를 같이 본다 | 같은 세션: 레이아웃만 본 QA 가 사용자가 문제 삼은 것을 놓침 |
| 파일명은 폴더 규칙으로 정하고 덮어쓰지 않고 버전을 올린다 | `questions.md` 1.4 |
| "N차년도 실적" 은 그해 하반기(2차) 워크샵 자료가 근거다 | `questions.md` 1.6 |

**구성** (사용자가 받아들인 워크샵 발표 자료의 장)

| 장 | 무엇 |
|----|------|
| I. 개발 범위 | 우리가 맡은 모듈과 범위 |
| II. 사업계획서 진행 사항 | 계획서 항목마다 어디까지 했는지 |
| III. 개발 현황 | 모듈마다 슬라이드. 실제 결과 화면 |
| IV. 진행 계획 | 남은 것과 다음 단계 |

다른 과제·행사면 사용자가 준 이전 발표 자료의 장을 따른다.

**pptx 를 고칠 도구.** why-hwp 는 pptx 를 다루지 않는다 (설계 결정). 슬라이드 글자는
`unzip -p <파일> ppt/slides/slideN.xml` 로 읽고, 고치는 데는 pptx skill 이 있으면 그것을 쓴다. 고칠 방법이 없으면 그렇다고 알리고,
슬라이드마다 "어느 상자에 무슨 글" 표와 그림 SVG 로 대신할지 **물어서 승인받은 뒤** 만든다. 요청한 것은 pptx 라서, 대체물은 승인 전에는 최종 산출물이 아니다 (외부 리뷰).

## 2. 발표·리뷰용 md

리뷰 회의에서 넘겨 보는 문서다. **근거 문서와 나눈다.** 이 문서는 그림과 핵심 세 줄,
`file:line` 과 기능별 상세는 근거 문서에 둔다 ("발표용그림이랑 같이 흐름 들어간 문서. 발표용/리뷰용 문서루써놔").

```markdown
# <대상> <주제> 현황

> **발표 · 리뷰용 문서입니다.** 그림 한 장마다 핵심을 세 줄 안팎으로 붙였습니다. 기능별 상세와 근거는 [상세 문서](<상세 문서>.md) 에 있습니다.

| 항목 | 값 |
| --- | --- |
| 목적 | <무엇을 리뷰하나> |
| 기준 소스 | <repo> `<브랜치>` `<커밋>` |

**목차**

1. 한 장 요약
2. 전체 구조
3. <흐름 1>
...
N. 리뷰에서 정할 것

---

## 1. 한 장 요약

- **<결론 1>.** <한 줄 설명>
- **<결론 2>.** <한 줄 설명>
- **강점은 <무엇>입니다.** <근거>
- **공백은 <무엇>입니다.** <근거>

| 수치 | 값 |
| --- | --- |
| <세는 것> | <값> |

---

## 2. 전체 구조

![전체 구조](assets/<그림>.svg)

- <그림이 말하는 것 1>
- <그림이 말하는 것 2>
- 리뷰 포인트: <부딪힐 자리>

---

## N. 리뷰에서 정할 것

**이 문서는 결정하지 않았습니다.** 판단이 필요한 항목만 골랐습니다.

| # | 성격 | 항목 | 왜 지금 보나 |
| --- | --- | --- | --- |
| 1 | 결함 | <무엇> | <안 보면 생기는 일> |
| 2 | 기능 공백 | <무엇> | <무엇> |

## 부록

| 무엇 | 위치 |
| --- | --- |
| 기능별 상세 · 근거 `file:line` · 확인 못 한 것 | [상세 문서](<상세 문서>.md) |
| 그림 원본 | `assets/*.svg` |
```

| 지킬 것 | 근거 |
|---------|------|
| 절마다 그림 한 장 + 핵심 세 줄 안팎 | 사용자가 받아들인 리뷰 문서 |
| "리뷰 포인트:" 로 부딪힐 자리를 짚는다 | 같은 문서 |
| 마지막 절은 "정할 것" 표. 결정하지 않는다 | `writing.md` 2절 |
| 맨 위 안내와 "기준 소스" 표는 리뷰 문서라서 둔다. 발표·공개 설계 문서에는 두지 않는다 | 리뷰 문서에서는 지적받지 않았고, 공개 설계 문서에서는 "맨위에 이거 없애" (판단으로 가른 것) |
| 그림은 스타일 A (`figures.md` 3절) | "머메이드 같이 딱딱한 그런 구조도 말고" |
| 같은 주제의 다른 과제와 비교하면 각 장 끝에 "<비교 대상> 은 이렇게 다릅니다" 절, 마지막에 비교 표 | "지금이 <우리 제품> 위주로 설명하고 <비교 대상> 는 이렇게 다르다는 식으로 가자" |
| 소스만 읽고 쓴 문서면 그렇다고 맨 위 안내에 밝힌다 ("제공한다" 는 "코드와 화면에 있다" 는 뜻) | 사용자가 받아들인 리뷰 문서 |
