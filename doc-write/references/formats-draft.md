# 붙여 넣을 초안

메일, MR·PR, Jira, Slack 에 사용자가 그대로 붙여 넣는 글이다.

## 1. 공통

| 규칙 | 근거 |
|------|------|
| **이전 초안이나 붙여 넣은 양식이 있으면 그 구성을 그대로 따른다.** 모듈이 하나여도 이전 초안의 제목 줄을 둔다 | "기존에 MR 했던거 처럼 MR 초안 작성해줘", "이 형식에 맞게 Jira티켓 초안 작성해줘" |
| 이전 초안은 그 폴더, 지난 세션 기록(`session-grep.sh`), repo 의 규약 skill 에서 찾는다. 못 보면 못 봤다고 밝힌다 | MR 초안 세션들 |
| **이름을 준 파일은 그 이름으로.** repo 안이면 `.claude/` 아래, 커밋하지 않는다 | "mr.md 로 뽑아줘", "jdk.md로 뽑아" |
| **모르는 값은 `<...>`, 비밀값은 "별도로 전달"** | 초안 세션들 |
| **초안에 약속이 들어가면 짚는다.** 보낼지, 그 일도 할지 묻는다 | Slack 답변 초안 세션 |
| 상황이 바뀌면(고쳤으면) 앞 초안을 버리고 새로 쓴다 | 같은 세션 |
| 공개 글(PR, 공개 이슈)은 내부 IP·호스트·사내 이름 0건을 확인하고 결과를 보고에 적는다 | 전역 규칙 PR 절 |
| 최소 분량. Jira 는 한 건 | `writing.md` 2절 |

## 2. 메일 (txt)

**txt 로 쓰고 마크다운 기호(`**`, 백틱, `#`)를 쓰지 않는다** ("아아 md 말고 txt").
받는 사람이 다시 물을 만한 것은 한 줄 미리 넣는다.

**릴리즈·핫픽스 안내**

```
제목: [<모듈>] <버전> <성격> 안내

안녕하세요, <이름>입니다.

<모듈> <버전> <성격>를 릴리즈했습니다.
<무엇을 담았는지 한 줄>. <무엇은 바뀌지 않았는지 한 줄>.

■ 수정 사항

[<묶음>]
1. <무엇이 어떻게 안 되던 문제>
   - <원인 한 줄>
   - <고친 것 한 줄>
     (<보충>)
2. <문제>

[<묶음>]
3. <문제>
   (<이제 어떻게 보이는지>)

■ <연동 repo> 반영
- <무엇> <옛 버전> → <새 버전>
- PR: <링크, 만들기 전이면 (생성 후 링크 기입)>

■ 릴리즈 노트
<링크>

감사합니다.
```

**문서 공유**

```
제목: [<과제>] <무엇> 공유 (<일정 항목>)

안녕하세요, <회사> <이름>입니다.

<일정의 어느 항목>에 따라 <무엇>을 공유드립니다.
<이것이 무엇인지 한두 문장>. <하지 않는 것 한 문장>.


1. 자료 위치 (<repo 주소>, <브랜치>)

 - <공통 문서>: <경로>
   (<담긴 것>)
 - 기관별 문서: <경로> (<기관>), <경로> (<기관>)


2. 접속 정보

 - 주소: <주소>
 - 인증: <방식>  (토큰은 별도로 전달드리겠습니다)


3. 기관별로 봐 주실 것

 - <기관>: <문서>의 <무엇>입니다.
   <한두 줄>


4. 시험 결과

 <어디서 무엇을 확인했는지 한 줄>
 - <환경>: <결과>


5. 알려진 제약

 - <제약>
 - <제약 묶음>
   . <세부>


문의나 요청은 이 메일로 회신 주시거나 <다른 경로>로 남겨 주시면 반영하겠습니다.

감사합니다.
<회사> <이름> 드림
```

| 틀 | 무엇 |
|-----|------|
| 제목 | `[모듈 또는 과제] 무엇 안내` |
| 첫머리 | 무엇을 했는지 두 줄과 무엇이 바뀌지 않았는지 |
| 절 | 릴리즈 안내는 `■`, 공유 메일은 번호 절 사이 빈 줄 두 개 |
| 절 안 | ` - ` 항목, 그 아래 세부는 `   .` 또는 들여쓴 `-`, 괄호 보충 |
| 제약 | 알려진 제약을 숨기지 않는다 |

## 3. MR 초안 (사내 GitLab)

repo 에 MR 규약 skill 이 있으면 그것이 먼저다. 없을 때 사용자가 받아들인 모양.

````markdown
# MR 초안 - <티켓> (<타깃 브랜치> 대상)

아직 만들지 않았다. 소스 브랜치는 push 했다.

```
Source Branch : <브랜치>   (<커밋>, origin/<타깃> <커밋> 기준)
Target Branch : <타깃>
Commit 수     : <N>개
squash: false / remove_source_branch: false
```

---

## 제목

```
[<티켓>] <한국어 한 문장>
```

## 본문

```markdown
## 변경 모듈
<모듈>

## 작업 내용
 1. [`<커밋>`](<커밋 링크>) [<티켓>] <커밋 제목>
    - <요약>
    - <요약>
      - <세부>

## 확인 결과
<무엇을 어떻게 확인했나 한 줄>

| 항목 | 전 | 후 |
|------|------|------|
| <항목> | <값> | <값> |

## 참고
- <확인하지 않은 것>
```

---

## 만드는 방법

1. 웹에서 직접 생성: <링크>를 열고 위 제목과 본문을 붙여 넣는다. squash 와 "소스 브랜치 삭제" 는 체크하지 않는다.
2. API 로 생성: `<호스트 변수>`·`<토큰 변수>` 가 있어야 한다.
````

| 규칙 | 근거 |
|------|------|
| `## 변경 모듈` 은 모듈이 하나여도 둔다 | 지난 세션 초안과 맞춘 일 |
| 커밋 본문이 비어 있으면 변경 코드를 읽고 요약을 붙인다 | MR 초안 세션 |
| 확인하지 않은 것은 `## 참고` 에 | 같은 세션 |

## 4. PR 본문 (공개 GitHub)

upstream 의 README·커밋 언어를 따른다. 기록이 없으면 그 근거로 정하고 밝힌다.
`## Summary`, `## Test plan`, 체크박스, 생성 도구 문구를 쓰지 않는다 (전역 규칙).

**기능 PR**

```
<prefix>: <what this adds>

<What this is and whose part it is, two or three sentences. What belongs to partners and how it is represented here.>

Processes

| Owner          | Binary  | Port | What it does |
|----------------|---------|------|--------------|
| <us>           | <name>  | <n>  | <one line>   |
| Partner (mock) | <name>  | <n>  | <one line>   |

Points for the partners

- <contract>: <what is ours, what is theirs>

How to try it

    <command>

Checked: <only what was actually run>
```

**버그 수정 반영 PR**

```
<What this PR bumps or changes, one sentence.>

Bug fixes in <module> <version>:
- <fix>

Breaking changes for API clients:
- <change and what clients must do>

Changes in this PR:
- <file>: <old> -> <new>

<What did not need changing and why, one line.>

Release notes: <link>
```

| 규칙 | 근거 |
|------|------|
| 우리 몫과 협업 기관 몫을 표로 가른다 | `writing.md` 2절 |
| "Checked:" 에는 실제로 돌린 것만 | `writing.md` 8절 |
| 올리기 전에 정할 것(경로, 조직 이름 공개 여부)은 본문 밖 표로 붙여 묻는다 | PR 초안 세션 |
| 만들기 직전에 제목과 본문을 보여 주고 승인받는다 | 전역 규칙 PR 절 |

## 5. Jira 티켓

붙여 넣은 양식의 제목을 마크다운 없이 그대로 쓴다.

```
작업 내용
<무엇을 조치하는지 한 문장>

<왜 필요한지 두세 줄. 지금 상태와 그것으로 부족한 이유>

작업 범위
<할 일 한 줄> (<모르는 값이면 <대상 목록>>)

<할 일 한 줄>
- <세부>
- <세부>

<할 일 한 줄>

참고사항
<판단의 근거 한두 줄>

검증한 것: <무엇>
- <확인한 것>
- <확인 못 한 것>

근거: <출처>, <직접 확인한 것> (<확인 날짜>)
```

| 틀 | 무엇 |
|-----|------|
| 작업 범위 | 한 줄짜리 항목을 빈 줄로 나누고, 세부만 `-` |
| 끝 | "검증한 것" 과 "근거". 근거의 날짜는 남긴다 |
| 대화에서 확인한 것만 | 모르는 대상은 `<대상 목록>` |

## 6. Slack 답변

글타래마다 따로 쓴다.

| 순서 | 무엇 |
|------|------|
| 1 | 결론 한 문장 ("네, 맞습니다.", "네, 의도한 동작입니다.") |
| 2 | 왜 그런지 |
| 3 | 상대가 할 일 ("시트의 기대결과를 `<값>` 으로 고쳐 주세요") |

고친 뒤 다시 쓰는 판은 "<버전> 에서 반영했습니다." 로 시작하고 바뀐 것을 번호로 쓴다.
