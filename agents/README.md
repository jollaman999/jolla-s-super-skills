# agents

[`verify-impl`](../verify-impl/) 이 부리는 전문 서브에이전트 8종입니다.
설치하면 `~/.claude/agents/` 에 걸립니다.

## 왜 나눴나

두 가지 이유입니다.

**컨텍스트를 격리하려고요.**
코드 통독과 로그 수천 줄이 팀원 쪽에서 끝나고, 팀장에게는 정리된 표나 JSON 만 올라옵니다.
팀장이 직접 다 읽으면 정작 판단할 때 컨텍스트가 남아 있지 않습니다.

**확증 편향을 깨려고요.**
자기가 통과라고 판정한 것을 자기가 다시 검토하면 잘 안 깨집니다.
그래서 반증 담당(`verify-refuter`)은 팀장과 컨텍스트를 분리해 두었습니다.

## 팀원

| 팀원 | 담당 | 성격 |
|------|------|------|
| `verify-inventory` | 외부로 노출된 기능을 진입점 기준으로 훑어 표로 | 코드를 많이 읽되 표만 올립니다 |
| `verify-target-scout` | 접속 대상(호스트·포트·인증 변수명)과 프론트 존재 탐색 | **시크릿 값은 절대 출력하지 않습니다** |
| `verify-crosscheck` | 기능과 API 스펙 대조. 미구현과 미문서화 찾기 | 접속 없이 정적으로만 |
| `verify-host` | 배정받은 호스트 한 대에서 체크리스트 전부 실행 | SSH 가 주력. 로그·DB·배포 대조도 |
| `verify-frontend` | 프론트가 부르는 경로와 백엔드 라우터 대조 | 계약 불일치는 양쪽을 같이 봐야 잡힙니다 |
| `verify-refuter` | 통과 판정 하나를 받아 **틀렸음을 입증하려 시도** | 기본 태도가 회의적입니다 |
| `verify-diagnoser` | 실패·분쟁 항목의 원인 추적과 수정안 | **진단만 하고 고치지 않습니다** |
| `verify-differ` | 호스트마다 결과가 갈릴 때 그 차이의 원인 | 같은 코드가 다르게 돌면 환경 문제입니다 |

## 공통 규칙

- **추정으로 판정하지 않습니다.** 실행한 명령의 출력, 직접 본 것, `file:line` 중 하나가 없으면 `unknown` 입니다
- **고치지 않습니다.** 진단 담당도 원인과 수정안까지만 올립니다. 고칠지는 사람이 정합니다
- **범위 밖은 보고만 합니다.** 작업 중 다른 문제가 보여도 손대지 않습니다
- **원격 명령에는 항상 timeout 을 겁니다.** 폴링에는 횟수 상한을 겁니다
- **비밀번호와 토큰은 파일에 쓰지 않고 출력에서 마스킹합니다**

## 직접 부르기

`verify-impl` 이 알아서 부르지만, 필요하면 개별로도 쓸 수 있습니다.
다만 각자 담당 노드의 입력을 전제로 하기 때문에 (예: `verify-refuter` 는 통과 근거가 되는 evidence 가 필요합니다)
맥락 없이 단독으로 부르면 결과가 얕습니다.
